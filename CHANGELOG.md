# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Admin HTTP: `AdminHttpServer.Builder.addTrustedProxy(...)` names a reverse proxy in front of the server, as an address or a range such as `10.0.0.0/8`. For a request from one of them the login throttle counts by the last address in `X-Forwarded-For` that is not a trusted proxy. Without the setting the header is ignored, as before, and the server logs one warning when a login carries it.

- `TaskClient.Builder.addRetryPolicyName(name)` tells a client which retry policy names the runners have. Once a name is added, `enqueue`, `enqueueAll` and `prepare` refuse a request that names any other policy with a `TaskValidationException`, so a wrong name is found when the task is enqueued and not when it first fails. A request that names no policy passes, and a client with no names added checks nothing, as before.
- Fault-injection tests for every store, in `bth4j-store-tests`. `FaultContract` cuts each store write before and after every round trip (a JDBC statement or commit, a Redis command, an in-memory call) and checks that the call throws, that the stored state is the one before or the one after and nothing in between, and that the same call sent again ends in the state of one clean call. `RunnerFaultContract` runs a runner and a client on a store whose calls fail at random, through a renewal outage, through a runner that loses its store for good and through a lost enqueue answer. They run on PostgreSQL, Redis, Valkey, SQLite and the in-memory store. [Fault-tolerance tests](docs/fault-tolerance-tests.md) lists what a resend answers for every call and how to run them on a store of your own.

### Changed

- SQLite: the writers of one `SqliteTaskStore` instance wait in line in the process before they start a write transaction. Before, they polled SQLite's write lock through its busy timeout, and a writer could lose every round and fail with `SQLITE_BUSY` after the timeout for a write that takes milliseconds. A second store instance or process on the same file, and `enqueue(Connection, TaskRecord)`, still wait by the busy timeout.
- Breaking: every store is made by a builder, and the public constructors are gone. A setting can be added to a builder later without another constructor.

  | Before | Now |
  |---|---|
  | `new RedisTaskStore(client, namespace)` | `RedisTaskStore.builder().client(client).namespace(namespace).build()` |
  | `new PostgresTaskStore(dataSource, namespace)` | `PostgresTaskStore.builder().dataSource(dataSource).namespace(namespace).build()` |
  | `new SqliteTaskStore(dataSource, namespace)`, also with a clock | `SqliteTaskStore.builder().dataSource(dataSource).namespace(namespace).build()`, with `.clock(clock)` for a test |
  | `new InMemoryStore()`, `new InMemoryStore(clock)` | `InMemoryStore.builder().build()`, with `.clock(clock)` for a test |

  `build()` refuses what the constructors refused, with the same messages. A null clock is a `TaskConfigurationException` on the in-memory store too.
- Breaking: `EnqueueResult.Accepted(id)` is `Accepted(id, created)`. `created` is true when this call stored the task and false when a task with this id and the same content was already there and nothing was written, so a caller that resends with its own ids can tell a first write from a repeat. A pattern `case Accepted(var id)` needs the second component.
- Breaking: an operator's pause, resume, trigger and delete of a schedule name the revision the operator saw, as the task actions do, and are refused when the schedule was replaced or re-timed meanwhile. Before, a delete clicked on an old view removed whatever definition had the id by then.

  | Before | Now |
  |---|---|
  | `AdminOps.pauseSchedule(id, paused)`, `triggerSchedule(id)`, `deleteSchedule(id)` returning `boolean` | `pauseSchedule(id, revision, paused)`, `triggerSchedule(id, revision)`, `deleteSchedule(id, revision)` returning `ScheduleOutcome`: `APPLIED`, `NOT_FOUND` or `STALE` |
  | `ScheduleView` without a revision | `ScheduleView.revision()`, its second component |
  | Admin HTTP: `POST schedules/{id}/pause`, `resume`, `trigger` without a body, `DELETE schedules/{id}` | the `revision` (a string, as the listing gives it) in the JSON body of the POST routes and as the query value `revision=` of the DELETE; a missing or malformed one is answered 400, a stale one 409 with the code `STALE`, an unknown id 404 with the code `NOT_FOUND` |
  | Store SPI: `deleteSchedule(id)`, `pauseSchedule(id)`, `resumeSchedule(id, nextFireAt)`, `triggerSchedule(id, fireAt)` returning `boolean` | each takes `Long expectedRevision` after the id (null for any) and returns `ScheduleOutcome`; the comparison and the write are one atomic step |

  `TaskClient.deleteSchedule(id)` names no revision and removes the definition whatever its revision is. [Changing a schedule that someone else changed](docs/recurring-tasks.md#changing-a-schedule-that-someone-else-changed) says what changes a revision. The dashboard sends the revision it shows.
- `claimBatchSize` and `purgeBatchSize` have no upper limit today. A later release may refuse values above about 10,000; [Configuration](docs/configuration.md) says what a very large value does.
- Breaking: names that misled, and adders that looked like setters.

  | Before | Now | Why |
  |---|---|---|
  | `BackgroundRunner.Builder.cancelledRetention` for CANCELLED and EXPIRED tasks | `cancelledRetention` for CANCELLED, new `expiredRetention` for EXPIRED (both 48 hours by default) | one setting decided two things |
  | `ScheduleDefinition.queue(String)`, `account`, `maxAttempts`, `maxRunTime`, `zone`, `misfire`, `overlap` (with an argument) | `withQueue`, `withAccount`, `withMaxAttempts`, `withMaxRunTime`, `withZone`, `withMisfire`, `withOverlap` | they return a changed copy and had the name of the accessor |
  | `TaskType.payloadVersion(int)`, `interruptOnCancel()` | `withPayloadVersion(int)`, `withInterruptOnCancel()` | the same |
  | `QueuePolicy.weight(int)`, `QueuePolicy.maxConcurrent(int)` | `QueuePolicy.ofWeight(int)`, `QueuePolicy.ofMaxConcurrent(int)` | factories with the name of the accessor |
  | `BackgroundRunner.Builder.queue(name, policy)`, `retryPolicy(name, policy)` | `addQueuePolicy(name, policy)`, `addRetryPolicy(name, policy)` | they add to what is there |
  | `AdminHttpServer.Builder.user(...)`, `corsOrigin(String...)` | `addUser(...)`, `addCorsOrigin(String)`, one origin per call | the same |
  | `TaskRequest.Builder.header(name, value)`, `headers(map)` | `addHeader(name, value)`, `addHeaders(map)` | the same |
  | `BackgroundRunner.Builder.recurringTasksCheckInterval`, `scheduledTasksCheckInterval` | `scheduleCheckInterval`, `scheduledTaskCheckInterval` | the API says "schedule"; one form for every interval |

  A runner that set `cancelledRetention` to keep expired tasks for another time sets `expiredRetention` too. A trusted proxy that is not an address or a range is refused with `trusted proxy <position> is not an IP address or a range such as 10.0.0.0/8`, where the position counts the proxies added so far.
- Breaking: one form for points in time and for yes-or-no questions, and no name that means two things.

  | Before | Now | Why |
  |---|---|---|
  | `TaskView.due()`, `TaskEvent.Rescheduled.due()` | `dueAt()` | a point in time ends in `At`, as `createdAt` and `claimedAt` did; deadlines keep their names (`leaseUntil`, `keyUntil`, `startBy`) |
  | Admin API: `due` of a task, `nextFire` of a schedule, `lastSeen` of a runner | `dueAt`, `nextFireAt`, `lastSeenAt` | the same |
  | `TaskContext.cancelRequested()` | `isCancelRequested()` | a question on a class or an interface starts with `is`, as `isQuiet()` and `isTerminal()` did; record components keep the plain name |
  | `EnqueueResult.accepted()` | `isAccepted()` | the same |
  | `Uniqueness.keepFor(d)`, `Uniqueness.KeepFor`, `Uniqueness.MAX_KEEP_FOR` | `keepAfterDone(d)`, `KeepAfterDone`, `MAX_KEEP_AFTER_DONE` | the time counts from the end of the task, not from the enqueue; the name says so, next to `UNTIL_DONE`. Stored data does not change |
  | `TaskContext.attempt()` | `attemptNumber()` | it is the number of this attempt; `TaskView.attempts()` is how many there were |
  | `TaskView.type()`, `ScheduleView.type()` | `typeName()` | they are the name; `TaskRequest.type()` is the `TaskType` |
  | `DefaultVtExecutor.getActiveTaskCount()` | `activeTaskCount()` | no other method started with `get` |
  | Store SPI: `TaskRecord.due`, `WorkerInfo.lastSeen` | `TaskRecord.dueAt`, `RunnerRecord.lastSeenAt` | as above |
  | Store SPI: `InspectionStore.getTask(id)` | `task(id)` | as above |
  | Store SPI: `ScheduleEffect.pauses()`, `applied()` | `isPause()`, `isApplied()` | as above |

  A script that reads a renamed field of the admin API gets no error: the field is missing. Events, `UnservedWork` and the admin API keep `type` for the type's name. Stored column and key names do not change.
- Breaking: every store calls its name a namespace and its version a schema version. `RedisTaskStore.LAYOUT_VERSION` is `SCHEMA_VERSION`, as in the two SQL stores, and the Redis messages say "schema version". `PostgresTaskStore` and `SqliteTaskStore` take a namespace, as `RedisTaskStore` does: the name every table starts with. A name that is not allowed is refused with `namespace must match ...`; the message said `prefix`. Table and key names do not change.
- Breaking: an application no longer needs a store-author type to read or list anything.
  - `TaskView` has no `record()` and no public constructor from a `TaskRecord`. `TaskView.builder()` makes a view by hand, for a test of an observer, a retry policy or an `AdminOps` fake.
  - `AdminOps.runners()` returns `RunnerView`: the runner's id, label, times, running count and accepting state, with the queues and task types it processes by name (`queues()`, `types()`). It returned the store's record with numeric queue and type ids.
  - Redis: the class `Keys` and `RedisTaskStore.keys()` are not public. Key names are an internal of the store; [the Redis store page](docs/stores/redis.md#inside-the-redis-store) lists the keys.
- Breaking: one word for the process that runs tasks. It was a "runner" in `BackgroundRunner` and `RunnerHealth` and a "worker" in the registry, the settings, the admin API and the dashboard; it is a runner everywhere. Stored names (the tables `<namespace>_worker`, the column `worker_id`, the Redis keys) are unchanged, so no data moves.

  | Before | Now |
  |---|---|
  | `BackgroundRunner.workerId()`, `RunnerHealth.workerId`, `TaskEvent.Started.workerId`, `TaskView.workerId()` | `runnerId` |
  | `BackgroundRunner.Builder.workerLabel(...)`, `workerStaleAfter(...)` | `runnerLabel(...)`, `runnerStaleTimeout(...)` |
  | `AdminOps.workers()`, `purgeStaleWorkers(...)` | `runners()`, `purgeStaleRunners(...)` |
  | HTTP `GET /api/v1/workers`; JSON fields `workerId` (task, health) and `workers` (overview) | `GET /api/v1/runners`; `runnerId`, `runners` |
  | dashboard page Workers | Runners |
  | store SPI: `WorkerInfo`, `allocateWorkerId`, `purgeWorkers`, `AdminStore.workers()`, `TaskRecord.workerId`, `ClaimRequest.workerId` | `RunnerRecord`, `allocateRunnerId`, `purgeRunners`, `runners()`, `runnerId` |

  A script or an alert that reads a renamed JSON field gets no error; the field is simply missing. Log lines say "runner" where they said "worker".
- Breaking: the types an application uses no longer live in the store-author package. `TaskState`, `StateCounts`, `QueueInfo`, `CancelOutcome`, `RetryOutcome`, `FailureInfo` and `StepResult` moved from `today.bonfire.oss.bth4j.spi` to `today.bonfire.oss.bth4j`; only the import changes. The new `DeleteOutcome` is there too. The JSON helper `common.Json`, which was public only for the other bth4j modules, is `internal.Json`; nothing in the package `today.bonfire.oss.bth4j.internal` is supported API.
- Breaking: `TaskClient.putSchedule` returns `PutScheduleResult(outcome, nextFireAt)`: whether the definition was created, changed or found unchanged (`PutScheduleOutcome`), and the next fire time it has. It returned only the time, and the outcome was only logged. `TaskClient.schedules()`, the map of schedule id to next fire time, is `nextFireTimes()`; `AdminOps.schedules()` lists the definitions.
- Breaking, store SPI: the schedule methods say "schedule" as the API does. The stored names (tables, columns, Redis keys) are unchanged.

  | Before | Now |
  |---|---|
  | `RecurringDefinition` | `StoredSchedule` |
  | `RecurringSchedule(definition, nextFire)` | `ScheduleEntry(definition, nextFireAt)` |
  | `spi.PutRecurringResult`, `spi.PutRecurringOutcome` | `PutScheduleResult`, `PutScheduleOutcome` in `today.bonfire.oss.bth4j` |
  | `putRecurring`, `deleteRecurring`, `pauseRecurring`, `resumeRecurring`, `triggerRecurring` | `putSchedule`, `deleteSchedule`, `pauseSchedule`, `resumeSchedule`, `triggerSchedule` |
  | `dueRecurring`, `commitRecurring` | `dueSchedules`, `commitSchedule` |
  | `recurringDefinitions()`, `recurringSchedules()` | `schedules()`, `nextFireTimes()` |
  | `ScheduleEffect.nextFire()` | `nextFireAt()` |

  `StoredSchedule` holds `Duration fixedDelay` and `Duration maxRunTime` where it held the millisecond numbers `fixedDelayMs` and `maxRunTimeMs`; the record cuts both to whole milliseconds, which is what every store keeps. `ScheduleView.nextFire` is `nextFireAt`.
- `TaskState.SCHEDULED` is documented as what it is: a task waiting for its due time, which is a delayed task, a task waiting for its next attempt, or an occurrence of a schedule created ahead of its fire time. Schedules themselves are not tasks; `AdminOps.schedules()` lists them.
- Breaking, stored data: the stores write a new schema version and `init` refuses everything written by 4.x or older: PostgreSQL 4, Redis 6, SQLite 2. There is no migration. Let the old runners finish their work, then start on a new namespace or SQLite file, or drop the old tables and keys.
  - PostgreSQL keeps every time in a `timestamptz(3)` column, so the database itself holds whole milliseconds. The code that read rows written with microseconds before 4.2.0 is gone, and the cursor of a task listing counts milliseconds.
  - The schedule row has a `triggered` column (PostgreSQL, SQLite) or a `trg` field (Redis).
- Breaking, store SPI: `ScheduleStore.setNextFire(scheduleId, nextFire)`, the operator's write, is `triggerSchedule(scheduleId, expectedRevision, fireAt)`, and `DueSchedule` has `triggered`. The store marks a triggered fire time until another write replaces it; see the fix for late triggers below. The runner's `setNextFire(scheduleId, revision, expectedFire, nextFire)` is unchanged. `StoreContract.writeOtherSchemaVersion(namespace)` lets the contract tests see `init` refuse another schema version. `StoreContract.removeSchemaVersion(namespace)` lets them see `init` refuse tasks that have no schema version.
- Breaking, store SPI: `ScheduleStore.commitSchedule` returns the new enum `CommitOutcome`: `STORED` when the definition advanced and the occurrence is stored, `SKIPPED` when the definition advanced and the occurrence was not stored because another task holds its unique key, `NOT_COMMITTED` when nothing was written. It returned `true` for the first two. The runner reports a skipped fire from that answer and no longer reads the occurrence back, which saves one store call per fire of a schedule with `Overlap.SKIP`.
- Breaking, store SPI: `InspectionStore.holdsKey(id, key)` is new. It tells whether the task with that id holds a unique key now, also after the task was removed inside the key's keep window, which `taskByKey` does not show. The client asks it for a resend whose `startBy` has passed (see the fix below).
- Breaking: `TaskRequest.Builder.uniqueKey` refuses a key that starts with `sched:` with a `TaskValidationException`. An occurrence of a schedule with `Overlap.SKIP` holds the key `sched:<schedule id>`, so an application task with such a key made that schedule drop its fires, and a fixed-delay schedule could stay parked behind it. `taskByKey` and `cancelByKey` still take such a key.
- Breaking: a step name with U+0000 is a `TaskValidationException`, and the step's body does not run. Since 4.2.0 the name was stored with U+FFFD in its place, so two step names that differed only there shared one checkpoint and the second step returned the result of the first without running.
- Breaking: a step whose result is too long to record (8192 characters in its stored form, or 65536 characters for the names and results of all steps of the task) ends the task DEAD at once, with a `TaskUnrecoverableException` from `ctx.step`. It threw `TaskValidationException`, which was retried, so the body of the step, which had already run, ran again in every attempt.
- A maximum run time is checked about once a second. It was checked once per lease renewal, every 20 seconds with the default lease, so a `maxRunTime` of five seconds could ask the attempt to stop after 25.
- `Overlap.SKIP` decides at the fire time. The runner creates an occurrence up to one `scheduleCheckInterval` before its fire time, and that was when it looked whether the previous occurrence was still open: a job that fires every minute and takes 55 seconds lost every second fire. A fire that is still ahead now waits while the previous occurrence is open, and is skipped only when its time has come and the previous one is still open. An occurrence that had to wait this way starts up to one check interval after its fire time.
- Breaking: queues are set up with one `Queues` value on both builders, and the built-in queue is `general`:
  - `Queues.of("general", "mail")` names the queues; the first is the default queue unless `.withDefault(name)` names another. `BackgroundRunner.Builder.queues(Queues)` and `TaskClient.Builder.queues(Queues)` take it, and `BackgroundRunner.Builder.processQueues(list)` names the queues a runner processes when that is not all of them. `configureQueues(available, toProcess, default)` and `TaskClient.Builder.queues(list, default)` are gone.
  - The default queue no longer depends on the builder. A runner took the first queue it processes and a client the first available one, so a runner with `configureQueues(["default", "mail"], ["mail"], null)` sent a task without a queue to `mail`, while a separate producer sent it to another queue or refused `mail`. A runner that processes a subset and relied on "the default is the first processed queue" names it with `.withDefault(name)`.
  - Without any setup there is one queue, `general` (`Queues.GENERAL`), in place of `Q:DEF`, `Q:LOW`, `Q:MED` and `Q:HIGH`. Those names suggested priorities that the runner never gave. Whoever relied on them passes `Queues.of("Q:DEF", "Q:LOW", "Q:MED", "Q:HIGH")`; otherwise metric tags, the HTTP API, the dashboard and pause commands show `general`.
- Breaking: `BackgroundRunner` and `AdminHttpServer` follow one lifecycle, and both are `AutoCloseable`:
  - `RunnerHealth.Status` has `STOPPING`. `stop()` reported `STOPPED` at once, while tasks could run for the whole shutdown timeout and beyond; a deploy script that waited for `STOPPED` and then ended the process cut them off. The runner now reports `STOPPING` until its last task, claim and service has ended, also after the shutdown timeout ran out, and `STOPPED` only then. A `switch` over the status needs the new branch.
  - `BackgroundRunner.stop()` returns `boolean`: whether everything had ended when it returned. It still returns after `shutdownTimeout` at the latest.
  - `start()` after `stop()` throws `IllegalStateException` on both, also when the object was never started. The runner logged a warning and did nothing.
  - `start()` on a started object does nothing on both. `AdminHttpServer.start()` threw `IllegalStateException`.
  - `AdminHttpServer.stop()` before `start()` now stops the server for good, as it does for the runner; a later `start()` worked before.
- Breaking: a cron schedule has no default overlap rule. `ScheduleDefinition.of(id, type, cron, overlap)` and `of(id, type, payload, cron, overlap)` take `Overlap.ALLOW` or `Overlap.SKIP`, and the factories without it are gone; a cron definition without a rule is a `TaskValidationException`. The default was `ALLOW`, with which a slow job piles up parallel runs, and `SKIP` drops fires, so neither is right without being chosen. Pass `Overlap.ALLOW` to keep what a definition did. A fixed-delay definition still defaults to `ALLOW`.
- Breaking, admin HTTP: `sessionTtl` is the lifetime of a session counted from the sign-in (12 hours by default), not the time since its last request. A dashboard tab that stays open asks the server every ten seconds, so a session never ended while its tab was open, for days on a shared machine. Only the sign-in sets the cookie now, with `Max-Age` equal to `sessionTtl`. An operator who keeps the dashboard open, and a script that keeps one session, sign in again when the lifetime has passed.
- Breaking: one exception model. Everything bth4j throws to refuse a call or to report a failure of its own extends `Bth4jException`, so one `catch (Bth4jException e)` covers it, except the decode helpers for store authors (`TaskState.fromCode` and `RecordJson`), which throw `IllegalArgumentException` for a value they cannot read; [Exceptions](docs/errors.md) lists them. The signals a processor throws (`TaskSignal`) stay outside it, so that such a catch in a processor cannot swallow them, and an object used in the wrong state (`start()` after `stop()`) still throws `IllegalStateException`.
  - Data that is sent or stored throws `TaskValidationException`. These threw `IllegalArgumentException`: `Uniqueness.keepAfterDone`, a malformed listing cursor, a `limit` below 1, a `liveWithin` or `staleAfter` that `AdminOps.unservedWork` and `purgeStaleRunners` refuse, a null or negative delay of `TaskRescheduleException`, `EnqueueFailedException.retryRequests` with a list of another size, a null connection in `enqueue(Connection, ...)` of the PostgreSQL and SQLite stores, and every argument check of the store SPI (`StoreArguments`, `ClaimRequest`, `QueueGrant`). `Misfire.catchUp(0)` threw `TaskConfigurationException`.
  - A setting of a runtime object throws `TaskConfigurationException`. `AdminHttpServer.Builder.build()` threw `IllegalStateException` for a missing `AdminOps`, user or session lifetime; `Builder.addUser`, `Builder.addTrustedProxy`, `new FixedExecutor(0)` and `MicrometerRunnerMetrics.bind` threw `IllegalArgumentException`.
  - `TaskStoreException` and `UnreadableTaskException` moved from the package `today.bonfire.oss.bth4j.spi` to `today.bonfire.oss.bth4j.exceptions`, where the others are.
  - `UnreadableTaskException` is no longer a `TaskStoreException`, so `catch (TaskStoreException e)` does not catch it. The store works, and the same call fails the same way until the task is repaired or deleted. `TaskClient.enqueue` with a caller id that belongs to such a task throws it as it is, as does the check of `enqueueAll` before its first write; both threw `EnqueueFailedException`, which told the caller to resend with that id, and the resend failed for as long as the task was there. A schedule with `Overlap.SKIP` whose open occurrence cannot be read is moved ahead with a `schedule-broken` issue while the other schedules go on; it ended the round as a store error.
  - `enqueueAll` keeps its recovery data whatever fails from its first write on: the failure is an `EnqueueFailedException` with `ids`, `settled` and `notStored`, and what failed is its cause. Only a `TaskStoreException` or a `TaskIdReusedException` was wrapped; any other failure lost the results of the chunks that were already written.
  - The message of a `TaskConfigurationException` no longer starts with `ERR11_Error in configuration `.
- Breaking: `TaskEvent.Expired`, `LeaseExpired` and `Deferred` carry the queue and the type of the task, as names: `Expired(id, queue, type)`, `LeaseExpired(id, queue, type, attempts, maxAttempts, dead)`, `Deferred(id, queue, type, reason)`. A queue or type that cannot be named is the text `unknown`. An observer could not tell which queue an expired task or a lost lease belonged to, and the Micrometer counter `bth4j.tasks` counted both under `type="unknown"` and `queue="unknown"`; it now carries the real tags, and `bth4j.deferred` has a `queue` tag.
- Breaking: `TaskEvent` is no longer sealed, so that an event kind can be added in a minor release: a `switch` over events needs a `default` branch. A component may also be added to an event record or a view record in a minor release, which breaks only code that constructs such a record or takes it apart.
- Breaking: `Issue.kind()` is the enum `Issue.Kind`, not text. `Issue.Kind.text()` is the text it was (`lease-lost`, `store-error` and so on), and the admin HTTP API sends the same texts as before.
- Breaking, store SPI: `MaintenanceStore.expire` returns `List<ExpiredTask>` (`ExpiredTask(id, queueId, typeId)`) in place of the ids, and `ExpiredLease` has `queueId`. A store reads both in the step that expires the task or lists the lease, and reports 0 for an id it cannot read.
- Breaking: an operator's cancel, retry and delete say what happened. The store decides in the same atomic step as the change, in a fixed order: no such task, then another revision, then a state that refuses.
  - `CancelOutcome` is `CANCELLED`, `REQUESTED`, `NOT_FOUND`, `STALE` or `FINISHED`. `STALE` also stood for a missing task and for a finished one, so a caller could not tell "reload and try again" from "there is nothing to cancel".
  - `RetryOutcome` is `RETRIED`, `NOT_FOUND`, `STALE` or `NOT_RETRYABLE`. `DUPLICATE` is gone: a retry that finds its unique key held by another task, which only damaged data can cause, throws `TaskStoreException` and changes nothing.
  - `AdminOps.delete` and `AdminStore.delete` return the new `DeleteOutcome` (`DELETED`, `NOT_FOUND`, `STALE`, `LEASED`) in place of a boolean.
  - Admin HTTP: a refused retry, cancel or delete answers from that outcome, without a second look at the task, and with a `code` in the error body: 404 `NOT_FOUND`, 409 `STALE`, 409 `WRONG_STATE` with a message that names the rule. The code `KEY_HELD` is gone. A retry of a task that is not dead, cancelled or expired answered the same 409 as a stale revision, and the dashboard asked to reload for both; it now asks only for `STALE`.
- Breaking: a queue argument of `AdminOps` is never null or blank. `tasks(state, queue, cursor, limit)` and `pauseQueue(queue, paused)` throw `TaskValidationException` for one; null meant every queue in `tasks`, and a blank name, or null in `pauseQueue`, meant the default queue. The new `tasks(state, cursor, limit)` lists every queue. Over HTTP a missing or empty `queue=` still lists every queue.
- Breaking: `ScheduleView.zone` is the zone id as text, not a `ZoneId`. `AdminOps.schedules()` threw for every schedule when one stored zone was unknown to the JVM (other time zone data, for example); it now lists them all.
- Breaking, admin HTTP: the by-key routes take the key as a query value, `GET tasks/by-key?key=` and `POST tasks/by-key/cancel?key=`. A path could not carry the keys `.` and `..`, which a client resolves away. The dashboard no longer trims the key it looks up.
- Breaking: `RedisTaskStore`, `PostgresTaskStore` and `SqliteTaskStore` are final, as `InMemoryStore` is. `RedisTaskStore` refuses a missing client or a namespace that is not allowed with a `TaskConfigurationException`, as the other stores do; it threw `IllegalArgumentException`.
- A missing `jsonMapper` is a `TaskConfigurationException`, not a `TaskDataException`:
  - `BackgroundRunner.start()` refuses to start when a registered task type has a JSON payload and the runner has no mapper. Such a runner started, claimed the tasks of that type and ended each one as dead.
  - `TaskClient.enqueue` throws it for a JSON payload on a client without a mapper; the Javadoc now lists it and `TaskDataException`.
  - `ctx.step(name, type, body)` throws it before the body runs. The body ran first and its result could not be stored, so every attempt of the task ran the body again.
- Runner settings that are now checked when they are set or when the runner is built, each with a `TaskConfigurationException`:
  - Every interval has a shortest value and is at most 100 years: `scheduleCheckInterval` at least 10 ms (any positive value passed, and one nanosecond polled the store without pause). A duration too long to count in milliseconds is refused; it threw `ArithmeticException`.
  - `concurrency` and `taskExecutor` together are refused; the executor won without a word.
  - `runnerStaleTimeout` must be at least three times `maintenanceCheckInterval`, which is how often the heartbeat is written; below that the purge removed live runners.
  - A queue name is at most 128 characters, as a task type name is.
  - `TaskType.of(name, (Class) null)` and `TaskType.of(name, (PayloadCodec) null)` are refused; the tasks of such a type ended as dead.
- `TaskRequest.Builder.retryPolicy(name)` takes a name of 1 to 64 characters (`TaskRequest.MAX_RETRY_POLICY_LENGTH`), the rule the runner has for the names it registers; null still means the default policy.

### Fixed

- Cron in a zone: the next fire time was wrong when it was asked for on a day the zone's clocks change in a way other than the usual hour at 02:00 or 03:00. In Australia/Lord_Howe (half an hour), `30 2 * * *` asked for at 01:30 on the night of the change answered the next day; in America/Santiago (midnight is skipped), a yearly `0 0 1 1 *` asked for at the moment of the change answered a year late. A fixed time asked for inside its repeated hour, for example `0 1 * * *` at 01:00:03 in America/New_York on the night the clocks go back, fired a second time an hour later. Fire times are now found by matching wall-clock times and placing each one with the zone's rules, and the rule for a repeated stretch is exact: an expression whose minute or hour field starts with `*` fires in both passes, every other expression in the first pass only. [Recurring tasks](docs/recurring-tasks.md#cron-definitions-and-time-zones) has the table.
- The maximum run time of an attempt and the duration in `TaskEvent.Succeeded` are measured as elapsed time. They were differences of two readings of the wall clock, so a clock that was set back during an attempt (a time-sync step, a restored virtual machine) let the attempt run that much past its `maxRunTime` before the runner asked it to stop, and a clock set forward ended it early.
- Queue weights hold when slots free up one at a time. The shares were cut from each claim's own slot count, so a claim for one free slot, the usual case on a runner with few slots or long tasks, gave a queue of weight 3 beside a queue of weight 1 every second slot instead of three in four. The runner now keeps, from claim to claim, what each queue is owed (smooth weighted round robin), so the ratio holds for any number of free slots. A queue at its `maxConcurrent` earns nothing while it is held there and gets no burst afterwards.
- PostgreSQL: registering a schedule that another caller registers at the same moment no longer undoes a commit in flight. `putSchedule` locked the row before it wrote, but when the row did not exist yet at the lock and existed at the write, the write waited for a runner's commit of the first occurrence and then judged the definition by what was visible before that commit: it forgot the running occurrence and replaced the parked fire time, so a second occurrence could start beside the first. A definition that is not there yet is now only inserted, and the next round locks the row that appeared.
- Redis: failing a task whose queue field cannot be read removes it from the leased index of every queue. Its entry stayed in the index of its real queue, so `counts()` showed a leased task that no longer existed.
- `MicrometerRunnerMetrics`: a scrape that falls into a refresh no longer reads zero for every `bth4j.tasks.state` gauge. The refresh set all gauges to zero and then to their new values; it now writes the new values and sets to zero only the queues that left the counts.
- `MicrometerRunnerMetrics.close()` keeps its tags taken until its meters are removed. A binding with the same tags made in between was handed the closing one's gauges, which were then removed.
- Admin HTTP: an error log line for a request in the 4.x form `tasks/by-key/<key>` no longer shows the key.
- The dashboard's demo API (`dashboard/dev/fake-api.py`) serves the by-key routes in their query form; a key lookup in the demo found nothing.
- Dashboard: what a page showed differed from what is stored in four places.
  - A payload is shown digit for digit. A number above 2^53 was rounded (`9007199254740993` read `9007199254740992`) and `1.10` read `1.1`, because the page parsed the JSON to lay it out.
  - The steps of a task are listed in the order they finished. Steps with numbers as names came first, in number order.
  - "Next to leave" says so when more than 200 tasks wait for a time, because it then looks at 200 of them and an earlier one can be missing.
  - A fixed-delay schedule shows no time zone; it showed UTC, which it does not use.
- Contract tests: a check that only holds inside a short time window (a 200 ms lease, for example) ends the test as skipped when the machine took longer than the window. On PostgreSQL and Redis, which read a real clock, such a test failed now and then under load. A time read from the store only counts as such a window after the test checked it against its own clock, so a store that writes a wrong time fails the test.
- The promotion loop no longer asks the store about every millisecond while the store's clock is behind the runner's (a host ahead of the database server, for example). A task that is due by the runner's clock and was not moved is asked about again after 1, 2, 4 ms and so on, up to `scheduledTaskCheckInterval`. A due time less than a millisecond ahead is waited for and starts the wait short again.
- `AdminOps.pauseSchedule`, `triggerSchedule` and `deleteSchedule` and `TaskClient.deleteSchedule` throw `TaskValidationException` for a null id; the null went to the store, which answered in its own way. `AdminOps.unservedWork(Duration)` throws `TaskValidationException` for a null window or one longer than 100 years, as it does for a negative one.
- A schedule that an operator triggered fires however late the runner takes it up. A trigger that waited longer than the misfire threshold (the larger of one minute and twice the recurring check interval), because no runner was up or the schedule was paused, was handled as a missed fire: with `Misfire.SKIP` no task was created and the trigger was lost behind a `schedule-misfire` issue. Contract tests cover the mark on every store.
- A runner no longer shares its settings with its builder: using the builder again (for a second runner, say) changed the queue policies, the runner label and every other setting of a runner that was built before and not yet started.
- A request with a caller id that is sent again is accepted when its `startBy` has passed since, or when its `delay` now ends after `startBy`. The check added for a `startBy` in the past refused such a resend, against the rule that a resend with the same id answers `Accepted`. This also holds when the task was removed meanwhile and only its unique key is kept.
- `BackgroundRunner.drain` compares its deadline in a way that survives the wrap of the nanosecond clock.
- Queue policies: a runner with one free slot gave it to the first queue with a share even when that queue was empty, so a busy queue behind it waited for as long as the first queue stayed empty; a queue whose weight earned no share of the free slots waited the same way while the queues with a share had nothing to run. The runner now claims the leftover slots for the queues that were skipped.
- A lost lease is reported once. It was logged, counted and its processor thread interrupted again on every renewal round until the processor returned.
- Recurring tasks: resuming a fixed-delay schedule while its task was still running set the next fire one delay from now, so with `Overlap.ALLOW` a second run started beside the first. The next fire stays parked until that task ends.
- The promotion loop measures the wait for the next due task on the runner's clock. With a clock behind the wall clock (a test clock, for example) it called the store about every millisecond.
- Store errors in the promotion loop reach `health()` and the issue list; they were only logged.
- The runner:
  - An `Error` in the service check (no native thread for a restart, for example) no longer ends the check for good.
  - `stop()` and `drain` work with a timeout too long to count in nanoseconds (above about 292 years); `stop()` threw and stopped nothing.
  - The heartbeat is written before the expired leases are worked off, so a large backlog cannot make the runner look gone.
  - A `claimBatchSize` from 536,870,912 no longer overflows the batch size of promotion, lease recovery and schedules, which then did nothing.
  - A runner stopped right after `start()` no longer leaves a `RejectedExecutionException` stack trace from the maintenance thread.

- A duration too long to count in milliseconds, such as `ChronoUnit.FOREVER.getDuration()`, is refused with a `TaskValidationException` as `maxRunTime` and as `Uniqueness.keepAfterDone`; it threw `ArithmeticException`.
- A `ScheduleDefinition` built with a blank cron text next to a fixed delay has no cron. The blank text was stored, and registering the same schedule with a null cron then counted as a change of its timing.
- A stopped runner reports `STOPPING`, and `stop()` returns false, while a maintenance job is still in a store call after the shutdown timeout. It reported `STOPPED`.
- A runner with adaptive concurrency that cannot be built, because the store's `init` fails, no longer leaves its monitor thread behind.

- SQLite: an idle runner's check for work no longer reads the whole backlog of a paused queue on every poll.
- `RetryPolicy.exponential` keeps doubling up to the cap; it stopped at base x 2^20, which is 2.9 hours for a 10 ms base.
- PostgreSQL: `schedules()` lists by the bytes of the id (`COLLATE "C"`), as the other stores do, whatever the collation of the database.
- Redis: a task listing leaves out a task that left the listed state between the read of the ids and the read of the records.
- PostgreSQL: the store reads the time when a statement starts (`statement_timestamp()`), not when its transaction began. `enqueue(Connection, ...)` in a long transaction of the caller judged key windows, due times and the created time by the start of that transaction, so a key whose window ended meanwhile still counted as taken.

- Redis: `fail` ends a task whose queue, lease or attempts field cannot be read, and removes it when it has no readable queue to stay in; `renew` answers "not owned" for a lease that cannot be read and renews the other leases of the call. Both raised a script error, which for `renew` failed every lease of the call.

## [4.2.0] - 2026-11-10

### Added

- `bth4j-sqlite`: `SqliteTaskStore`, a store on SQLite 3.45 or newer (latest recommended, tested on 3.54) for runners on one machine, in one process or in several, with the database file on a local disk. It uses only `java.sql`: the application supplies the JDBC driver and a `DataSource`. `init` refuses a connection that is not in WAL mode or whose `busy_timeout` is below 1000 ms and names the setting; `synchronous` is the application's choice. Every write runs in a `BEGIN IMMEDIATE` transaction, the tables are `STRICT`, times are epoch milliseconds from the `java.time.Clock` given to the store, and the schema version is 1. `enqueue(Connection, TaskRecord)` joins the caller's transaction. The store passes the contract tests in the `test` phase, without Docker.
- Documentation: the README is a short front page, and the guides are focused pages under `docs/` with tables and diagrams. [Stores](docs/stores.md) says how the stores differ: which clock decides, what a crash can lose under each durability setting, memory eviction, enqueueing inside your own transaction (with an outbox for Redis), SQLite's single writer, Redis claims behind tasks past `startBy`, the order of tasks due at the same time and maintenance batches.

### Changed

- Limits every store can keep, refused when a value is handed in:
  - Times: one limit, `TaskRequest.MAX_TIME_FROM_NOW`, 36,525 days (100 years). The client refuses with `TaskValidationException` an `at` or `startBy` further than that from now, either way, and a longer `delay`; `ScheduleDefinition` refuses a longer fixed delay; the runner builder refuses with `TaskConfigurationException` a longer `leaseDuration`, `succeededRetention`, `deadRetention`, `cancelledRetention` or `workerStaleAfter`. `Uniqueness.keepFor` accepts at most `Uniqueness.MAX_KEEP_FOR`, the same value, and throws `IllegalArgumentException` beyond it. `AdminOps.purgeStaleWorkers` throws `IllegalArgumentException` for an age that is not positive or is longer (a negative age removed every worker row). A retry policy or a `TaskRescheduleException` that asks for a longer wait gets 100 years.
  - Text: no store is given U+0000, which PostgreSQL cannot keep. The client refuses it with a `TaskValidationException` in an account, unique key (also for `taskByKey` and `cancelByKey`), header name or value, retry policy name, encoded payload, schedule id or schedule account, and in an operator's cancel reason; a task type name, queue name or worker label with it is a `TaskConfigurationException`. Text from processor code (the failure message and stack, progress, step names and results, and the message of a `TaskCancelledException`) is recorded with U+FFFD in its place.
  - `ScheduleDefinition.account` follows the task rule, at most 128 characters.
- Redis: `init` refuses a server whose `maxmemory-policy` is not `noeviction` with a `TaskConfigurationException` that names the setting, because any other policy lets Redis remove task data or the keys that hold unique-key windows. When the connection may not run `INFO` (an ACL without `+info`, a renamed command) or the reply has no `maxmemory_policy`, `init` logs a warning to the new logger `Loggers.REDIS_STORE` and starts without the check.
- Recurring tasks: an invalid cron expression or time zone is logged as one ERROR line with the reason, without a stack trace; other failures to evaluate a definition still log the stack trace. `Cron.next` throws `TaskValidationException` for an expression that does not parse, with the message of `Cron.validate`, instead of the cron library's `IllegalArgumentException`.
- Store SPI: the stores behave alike in these points, and the contract tests check each one.
  - `StoreArguments` holds the argument checks: a null or blank queue or type name, a null worker label, a null `reschedule` due, a batch size below 1 and a purge of a state that is not terminal throw `IllegalArgumentException` with the same message on every store, and a pause of a queue id that was never registered is ignored. Every time the library hands a store lies within `TaskRequest.MAX_TIME_FROM_NOW` of now.
  - A new task starts without run fields on every way in (`enqueue`, `enqueueAll`, `enqueue(Connection, ...)`, `commitRecurring`): a store ignores the record's attempts, worker, lease, claim time, key-until, cancel request and reason, progress, steps and failures. `TaskRecord.asNew()` gives a record in that form. Before, each store kept a different set of these fields; the client never sends them, but a record copied from `getTask(...).toBuilder()` carries them.
  - Times and durations are kept in whole milliseconds: a store drops what is finer from those it is given, takes its own clock to the millisecond and compares a time it is given with a stored one to the millisecond.
  - The Javadoc states the rest: `purge` removes the oldest finished tasks within each queue, and a removed task whose key window is open leaves its key taken (the Javadoc said such a task is kept, which no store did); `taskByKey` is empty when only such a key stays taken; `counts()` covers every registered queue; `RetryOutcome.DUPLICATE` never comes from a store that lets only one task record carry a key at a time (PostgreSQL, SQLite); text is stored as given, so an empty string reads back empty; `promote`, `reclaim`, `purge`, `releaseKeys` and `expire` fill their batch while more tasks qualify, because the runner stops a round at the first short batch; a cancel request on a running task stays with it when the attempt fails with a retry, reschedules or is unclaimed, and a cancel or `finishCancelled` without a reason removes an earlier reason.
- The Redis integration tests run on Redis 8.10 (image `redis:8.10-alpine`), the latest stable release.

### Fixed

- PostgreSQL:
  - A new recurring occurrence is stored at the random revision the runner gives it, as 4.1.0 describes; it was stored at revision 0. Occurrence ids are always new, so no stale lease could match one.
  - A processor failure whose message or stack trace contains U+0000 is recorded, and so are progress and cancel reasons with it. Before, the write was rejected, the failure was lost, and the task stayed LEASED until its lease ran out.
  - Times and durations are kept in whole milliseconds; they were kept in microseconds. The store takes its own time as `current_timestamp(3)`. Rows written by 4.1.0 keep their microseconds until written again: their schedules still fire, and their tasks are listed once across pages.
- PostgreSQL and SQLite: `commitRecurring` stores the occurrence's `retryOf`; it was dropped (the runner never sets it on an occurrence).
- Redis and PostgreSQL: a task with a very long `keepFor` window can finish. Before, `ack` failed for every attempt (Redis from somewhere between 1,000 and 5,000 years, PostgreSQL from about 5.9 million years).
- Redis:
  - A task that went back to waiting (a failure with a retry, a reschedule or an unclaim) no longer keeps the worker of the attempt that ended, so once it is cancelled or expires `workerId` is null.
  - An empty progress or cancel reason reads back empty; it read back as null.
  - A cancel without a reason (`cancel`, `finishCancelled`, `finishCancelledExpired`) removes the reason of an earlier request; the earlier reason was kept.
  - A null `reschedule` due is refused with `IllegalArgumentException`; it threw `NullPointerException`. A null worker label is refused; it was stored as empty text.
- In-memory store:
  - Times and durations are kept in whole milliseconds, and its clock is read to the millisecond; it kept the full precision of its clock. `putRecurring` returns the next fire time as stored.
  - Arguments are checked as on the other stores; it accepted a null due, a null or blank name and a null label.
  - `counts()` covers every registered queue; it left out a queue without tasks.
  - Paging through tasks due after 2262-04-11 ends; the cursor overflowed and the walk repeated its first pages forever.
  - `purge` throws `IllegalArgumentException` for a state that is not terminal; it removed the live tasks.
- Redis and the in-memory store: a pause of a queue id that was never registered is ignored; it was kept, so a queue registered later under that id started paused.
- A retry policy or a `TaskRescheduleException` whose delay goes past what `Instant` or the store can hold (for example `ChronoUnit.FOREVER.getDuration()`) no longer leaves the task leased for good. Before, the end of the attempt could not be written, maintenance failed the same way at every round, and a full reclaim batch of such tasks at the head of the expired leases stopped every expired lease behind them from being recovered.

### Added

- Adaptive concurrency with CPU and memory targets: `Concurrency.adaptive(min, max, cpuTarget, memoryTarget)` (defaults 0.90 and 0.80 with `adaptive(min, max)`), and `Adaptive.withMemorySignal(MemorySignal.HEAP_AND_SYSTEM)` to count system memory as well as the heap (`MemorySignal.HEAP` is the default).
- `BackgroundExecutor.claimed(reserved, claimed)` tells the executor whether a claim filled its reservation, the demand signal of adaptive concurrency. `BackgroundExecutor.limit()` and `BackgroundRunner.concurrencyLimit()` report the current limit; the Micrometer gauge `bth4j.runner.concurrency.limit` exposes it.
- Workers record the queues and task types they process and whether they accept work (`WorkerInfo.queueIds`, `typeIds`, `accepting`); `quiet()` and `resume()` publish the state with an immediate heartbeat.
- `AdminOps.unservedWork()` (one-minute heartbeat window) and `unservedWork(Duration)` report queued work that no live accepting worker can take: a queue no such worker processes, or a task type none of a queue's such workers registered, with exact counts. Paused queues are skipped. `GET /api/v1/unserved` serves them, the Overview page shows them, and the Workers page lists each worker's queues, types and quiet state.
- `InspectionStore.queuedByType()`: exact QUEUED counts by queue and type.
- `ExecutionStore.ackAll(leases, keep, keepPayload)` acknowledges several tasks without a schedule effect in as few round trips as the store allows; the default calls `ack` for each. The runner sends the acknowledgements of tasks that finish while an earlier batch is on its way as one batch, with no timer and no added delay when it is quiet. Redis runs one script per 256 tasks and PostgreSQL one statement for the batch.
- `UnreadableTaskException`, a `TaskStoreException` with the task id, for a task with a stored value that cannot be read; `InspectionStore.getTask` throws it. The task listings leave such a task out (a page can then hold fewer than `limit` tasks while `next` is not null), and `counts()` still counts it.
- `DefaultVtExecutor(Concurrency.Adaptive, Consumer<String> issues)` is told once per signal when the CPU or a configured memory reading goes 5 s without a valid value; the runner raises it as the issue `resource-signal-unavailable`, and the executor logs it at WARN.
- `BackgroundExecutor.executeWithSlot(SlotTask)` runs a task that may free its slot before it ends. The default keeps the slot until the task ends, as `execute(Runnable)` does; `FixedExecutor` and `DefaultVtExecutor` free it early.

### Changed

- Adaptive concurrency starts at `min` and samples every 500 ms: whole-machine CPU (smoothed) and memory (the lowest reading over 2 s per component, so the GC sawtooth does not count). Growth requires occupied slots at or above the limit, including permit debt, and resource headroom. A full reservation claim provides demand evidence for 5 s and allows one growth step; a partial or empty claim clears it. With fresh evidence growth is about +25 % per step (at most 16 slots) far below the targets, +1 near them; without it, a saturated runner probes by +1 at most once per 5 s under the same resource checks and cooldowns. Free slots prevent growth. CPU above target for 1 s takes 20 % off, memory at target for 1 s takes 25 % off and blocks growth for 5 s, and memory at 95 % drops straight to `min`. Reductions use the highest valid memory component; growth needs every configured component valid. An unavailable signal blocks growth and decays the limit after 5 s. After 30 s without a running task observed at a tick or a nonempty claim, the limit resets to `min`; empty polling does not count as activity. Running tasks are never stopped; a lower limit admits fewer new ones. The throughput heuristics and the fixed 80 % CPU threshold are gone.
- Breaking: `Concurrency.Adaptive` has the components `cpuTarget`, `memoryTarget` and `memorySignal` (the two-argument constructor remains); `Concurrency.adaptive(min, max)` returns `Adaptive`; `FixedExecutor.limit()` returns `OptionalInt`.
- SPI: `ExecutionStore.claim` leaves out a claimed task it cannot read and ends its lease at once, returning the other tasks; `fail` and `failExpired` must work for a task with stored values that cannot be read, so such a task can still end (PostgreSQL drops stored failures it cannot read).
- Breaking SPI: `ClaimRequest` takes non-empty, distinct `QueueGrant(queueId, share, cap)` entries instead of queue ids. A store applies the share pass and the refill pass for every queue atomically in one call, honours caps and the total count, and leaves tasks of unknown types untouched, including their due time.
- Breaking SPI: `TaskStore.allocateWorkerId(label, queueIds, typeIds)`, `AdminStore.heartbeat(workerId, label, queueIds, typeIds, running, accepting)` and `InspectionStore.queuedByType()`; `WorkerInfo` adds `accepting`, `queueIds` and `typeIds`; `AdminOps` implementations must add `unservedWork(Duration)`. `GET /api/v1/workers` adds `accepting`, `queues` and `types`.
- `InspectionStore.tasks` (and the task listings of `TaskClient`, `AdminOps` and `GET /api/v1/tasks`) lists QUEUED and SCHEDULED tasks by due time, then id; the other states stay ordered by state change time, then id. Redis already listed waiting tasks by due time; PostgreSQL and the in-memory store now do too, so all stores agree. A cursor taken before the upgrade for those two states may skip or repeat tasks; start the listing again. Custom stores must order the same way.
- Breaking: Redis layout 5. Queued tasks live in one zset per queue and type, `q:<qid>:<tid>`, and `active:<qid>` holds the types whose zset is not empty. A claim intersects that set with the runner's stored type set `ts:<digest>`, so it reads only types that have queued tasks; counts, listings and the exact per-type counts read only those too. Before this, a claim read one zset per known type: with 10,000 registered types and tasks of 4, one Redis measured about 650 tasks/s against 7,900 with 10 types, and one idle runner used 11 to 13 % of the Redis core. On the 4.1.0 build the same runs (20,000 tasks, 64 slots) reach 18,500 to 21,600 tasks/s with 10,000 types, and the idle runner uses 0.4 %. Finished tasks are listed, counted and purged from one zset `idx:<state>:<qid>` (the `rm:` zsets are gone). Enqueue batches run one script per 64 tasks. Type storage names are `seq:type`, `reg:type` and the task hash field `ty`. Worker hashes have the fields `queues`, `types` and `accepting`, and a heartbeat is one script. The type set `ts:<digest>` is written with its expiry in one script. `init` accepts only layout 5 and refuses every other layout, including one written by 4.0.0 (layout 3) or an earlier 4.1.0 snapshot (layout 4); there is no migration, start those with a new namespace.
- A task frees its executor slot when its processor returns, before its outcome is written, so the slot takes the next task while the outcome is on its way to the store. The task stays running, with its lease renewed, until the store answers. `FixedExecutor` and `DefaultVtExecutor` let at most twice their current limit run or write their outcome at once, so a slow store still holds back claims; adaptive concurrency counts the slots this bound holds back as occupied. `runningTasks`, `RunnerHealth.runningTasks`, the heartbeat count and `bth4j.runner.running` include tasks whose outcome is still being written, so they can reach twice the limit. Observers of outcome events run after the slot is freed. Queue caps (`maxConcurrent`) still count a task until its outcome is written, and such an attempt is neither asked to stop nor abandoned for its maximum run time while it waits for the store. A thread waiting in an acknowledgement batch is woken only when its batch returns or when it is to send the next one, not on every batch. Measured on Redis with 50,000 no-op tasks and claim cap 64, alternating runs before and on the 4.1.0 build: concurrency 24 about 9,100 -> 13,400 tasks/s, 64 about 15,900 -> 21,400, 128 about 20,700 -> 29,100, 256 unchanged at about 29,000 (claims were already full); at 64 client CPU per task fell from about 70 to 45 microseconds and Redis CPU from about 41 to 35. Adaptive concurrency 12 to 256 on 200,000 no-op tasks went from about 6,700 to 11,600 tasks/s. Tasks that run for milliseconds gain much less, since the slot was held for about 1.5 ms of acknowledgement per task.
- PostgreSQL claims and acknowledgements cost less database work. A claim is one statement (both passes, no transaction round trips) that finds the picked rows by primary key; the known type ids go once per claim, sorted, as a value the planner does not estimate id by id, so a runner with thousands of types no longer plans each claim anew (about 7 ms at 10,000 types) or makes the database sort the ids on every index scan. Batched acknowledgements are one statement per batch instead of one commit per task. Measured on one PostgreSQL 18 container (fsync on) with 20,000 tasks and 64 slots, before and on the 4.1.0 build: database CPU per executed task fell from about 700 to 80 microseconds and throughput rose from about 4,300 to 11,100 tasks/s, with 10,000 registered types from about 2,000 to 8,500; an idle runner with 10,000 types claims in 0.03 ms instead of 0.8 to 4.7 ms.
- PostgreSQL 16 or newer is supported, 17 or newer recommended; the tests run on 18. 4.0.0 named PostgreSQL 10 as the minimum, which was never tested.
- Breaking: PostgreSQL schema 3. Task types are stored in `<prefix>_type` with `type_id` columns in tasks and schedules (the storage names were `event` and `event_id`). `<prefix>_worker` has `accepting boolean NOT NULL` and `queue_ids` and `type_ids` as `smallint[] NOT NULL`. The queued index also covers `type_id`. `payload_version` and `catch_up_max` are `integer` instead of `smallint`, so values above 32767 are stored instead of failing the write (and with it a whole batch). `counts()` reads a new index `<prefix>_task_counts (queue_id, state)`, listing one finished state of one queue reads `<prefix>_task_finished_queue`, and listing QUEUED across all queues scans the queued index once per queue and merges the results. A task removed inside its unique key window leaves a key-only row (state code 7, content columns empty) until the window ends. `init` refuses tables written by 4.0.0 (schema version 2) before it changes anything; there is no migration, use a new prefix or drop the tables. Tables of an earlier 4.1.0 snapshot also report schema 3 but lack these changes; drop them.

- A task removed inside its unique key window (`succeededRetention` or `deadRetention` zero at the transition, or purged after its retention) no longer stays readable until the window ends; only its key stays taken. Retention decides how long a task stays readable, `keepFor` how long its key blocks a same-key enqueue, which still answers `Duplicate` with the removed task's id. Purge removes such tasks like any other and counts them as removed; `taskByKey` is empty for them and `cancelByKey` answers `NOT_FOUND`. Redis keeps only the key string `k:<key>` until the window ends, PostgreSQL a key-only row, the in-memory store a key entry.
- New tasks and new recurring occurrences start at a random revision instead of 0. A worker that still held the lease revision of a removed task could renew, save steps on or acknowledge a new task that reused its id (a caller-supplied id) at that task's first revision; such a match is now about one in a billion. The cost is one `ThreadLocalRandom` call per record.
- Breaking SPI: `ScheduleStore.putRecurring` returns `PutRecurringResult(outcome, nextFire)` with the next fire time it stores, also when it kept the existing one. `pauseRecurring(id, paused)` is replaced by `pauseRecurring(id)` and `resumeRecurring(id, nextFire)`, which writes only a paused definition and, with a non-null `nextFire`, replaces its next fire under a new revision. The operator `setNextFire(id, at)` also forgets the recorded occurrence. `commitRecurring` with an occurrence id that belongs to an existing task writes nothing and returns false. Custom stores must adapt.
- A cancel request now wins over a voluntary `TaskRescheduleException`: the task ends CANCELLED instead of being rescheduled, so a body that reschedules itself on every attempt can still be cancelled.
- `Misfire.catchUp(maxFires)` after a downtime of more than `maxFires` fires moves in one step to the last `maxFires` missed fires and creates them from that check on (up to about 100 per check), with one `schedule-misfire` issue, instead of advancing one missed fire per check. Beyond 100,000 missed fires it creates one task now, as `FIRE_ONCE_NOW` does, with an issue.
- Repeated store errors with the same text are one `store-error` issue whose detail carries the count and whose time is the latest, so a store outage no longer pushes every other issue out of the 100-entry buffer.
- `AdminHttpServer.start()` after `stop()` throws `IllegalStateException`; build a new server instead. Before, a restarted server used an executor that was already shut down, or with an external executor kept the old sessions valid.
- Breaking: `EnqueueFailedException.retryRequests(requests)` returns only the requests after the completed chunks, and the new `settled()` holds the results of those chunks (`storedCount()` is its size). Before, the retry list sent the settled requests again, so a request that had answered `Duplicate` could be stored once its key's holder had finished, running work the first call had deduplicated. A batch's results are `settled()` followed by the retry's results. The constructors take the settled results instead of a count.
- The admin HTTP server keeps a random salt per user and the SHA3-384 digest of salt and password, instead of the unsalted SHA-256 digest, so equal passwords no longer give equal digests in a heap dump.
- `AdminHttpServer.Builder.secureCookie(boolean)` marks the session cookie `Secure` behind a TLS-terminating proxy; by default it is `Secure` only when the server has an `SSLContext`.

### Fixed

- Redis: a claim by a worker that does not handle a task's type pushed that task 5 s back in the shared queue, which delayed the workers that could run it, repeatedly while the others kept polling. Claims now read only the queues of the worker's types, merged by due time, so foreign tasks are neither touched nor counted against the scan budget.
- Weighted queue claims made up to two store calls per queue, and a failure after the first call left the tasks already claimed to wait for lease expiry. The runner now sends every queue's share in one claim: one script on Redis, one statement on PostgreSQL.
- Queue caps: when a claim found nothing because a queue was at its `QueuePolicy.maxConcurrent`, the runner slept the full `idlePollInterval` (500 ms by default) even after a task of that queue finished. It now claims again as soon as a task of a capped queue finishes, also after the task processor thread was restarted.
- Queue weights whose sum, or whose product with the free slots, exceeded an `int` overflowed when a claim split the slots, so queues got wrong or negative shares. The split now computes in `long`.
- `stop()` publishes at once that the runner accepts no more work (a heartbeat with `accepting` false), so `unservedWork` no longer counts a stopped runner as serving its queues until its heartbeat ages out.
- A maintenance job (lease reclaim, start-by expiry, heartbeat, purge) or the adaptive concurrency sampler that threw an `Error` was never run again, silently; the runner kept reporting the service as running. Each now logs the error and runs again at its next interval.
- A claim whose store returned more tasks than the runner asked for inflated the executor's slots for good. The extra tasks now go back to their queue unrun and the runner raises a `store-error` issue.
- A failed acknowledgement batch made every task in it log the full stack trace and add its own `store-error` issue, so one failure of up to 256 tasks pushed every other issue out. The error is now one issue and one stack trace; the other tasks log one line each.
- A claimed task with a stored value that cannot be read (a malformed number, state code or JSON field) failed the whole claim. The other tasks of the claim waited for their lease to expire (60 s by default) and lost an attempt; on PostgreSQL with auto-commit off the claim rolled back, so every later claim of those queues failed the same way. The unreadable task then stayed LEASED for good, because maintenance could not read it and logged an error every cycle; once a full reclaim batch could not be handled, maintenance read the same batch again at once, without end. Now the claim returns the other tasks and ends the lease of the unreadable one, and maintenance ends it DEAD within one check interval with the failure `unreadable-record`, raises the issue `corrupt-task` and emits `LeaseExpired` with `dead` true. Maintenance also stops reading expired leases for the cycle when a full batch could not be handled. On Redis, a task hash with an unreadable start-by, revision or attempt count no longer aborts the claim script halfway (which left the tasks it had already leased in no queue), and lease reclaim reads each expired lease on its own, so one malformed field no longer stops every reclaim. A header map with a null value counts as unreadable instead of failing with a `NullPointerException` outside this recovery. `AdminOps.cancel` and `delete` work on such a task given its id and revision; a corrupt fixed-delay occurrence is then not treated as one, so its definition is neither paused nor re-armed. The admin HTTP API answers 422 with code `UNREADABLE_TASK` when it has to read such a task, instead of 500 with a stack trace in the log. A task listing no longer fails on such a task: it leaves the task out and walks on past it, so the DEAD listing where it ends up keeps working.
- Adaptive concurrency without a valid CPU or memory reading (some containers and JVMs do not provide one) held the limit at `min` and said so only in DEBUG logs. It now logs a WARN and raises the issue `resource-signal-unavailable` the first time a signal goes 5 s without a valid reading.
- Redis: a stored task value that cannot be read or a claim reply of an unexpected shape fails with a `TaskStoreException` naming the task (an `UnreadableTaskException` for a stored value), instead of a raw `NumberFormatException`, `ClassCastException` or `NullPointerException`; PostgreSQL threw a raw `IllegalArgumentException` and now throws `UnreadableTaskException` too. The message does not quote stored values; the cause has the details.
- A runner whose worker row was deleted while it lived, for example after it could not reach the store for longer than `workerStaleAfter`, stayed out of `admin.workers()` until it restarted, because its heartbeat only updated an existing row. `unservedWork` meanwhile reported its queues as unserved although it was processing them. The heartbeat now writes the row again under the same id with the runner's label, queues and types, so the runner is listed again within one `maintenanceCheckInterval`.
- Dashboard preview API returns the cursor task-page shape on the first page too.
- A lease renewal round that ran while a finished attempt was still writing its outcome or emitting its events counted that attempt as lost: it logged "N of M leases could not be renewed, those tasks were taken over" and raised a `lease-lost` issue although nothing was taken over. Renewal now ignores such attempts; a real takeover still shows in the outcome write itself (`Outcome.LOST`).
- The lease renewal thread ended for good when a renewal round threw an `Error`, so every running task lost its lease while the runner reported RUNNING. It now logs the error and goes on, and the service monitor starts a new renewal thread if the old one died.
- A claim that threw an `Error`, a claimed task whose execution could not be built, or an `Error` from the executor left the reserved executor slots taken for good and the claimed tasks leased until their lease expired. Slots not handed to an execution are now released and unsubmitted tasks go back to their queue on every exit.
- `drain` could answer true while a claim that started before `quiet()` was still in progress, so a task leased by that claim ran after the drain returned. `drain` now also waits for such claims.
- Running attempts were tracked by task id, so when one runner ran two attempts of a task (an old one after lease loss and its retry), the first to finish removed the other from lease renewal and from `drain`. Attempts are tracked one by one.
- A task processor that the service monitor restarted after `quiet()` claimed again, because it did not see the quiet state. Every processor generation now shares one admission state.
- A `start()` that failed after starting some services, for example when the store could not be reached, left them running and the runner unusable. It now stops what it started and can be called again.
- `stop()` could wait `shutdownTimeout` once per service and again for the executor, and without end when a start stuck in a store call held the lifecycle lock. It now keeps one deadline for the whole stop.
- Maintenance used the default retry policy without notice when an expired lease named a policy the runner does not have; it now raises the `retry-policy` issue as the processor does.
- A pending cancel request interrupted an `interruptOnCancel` body again on every renewal round; it now interrupts it once.
- A store failure while committing a recurring occurrence was logged as a skipped definition without a `store-error` issue, and the round went on to try every other due definition against the failing store. It now raises the issue and ends the round.
- A recurring definition that cannot be evaluated (an invalid cron expression, a time zone the JVM no longer knows) was skipped on every round and stayed first in line, so with enough of them the definitions behind it never fired. It is now moved ahead by at least an hour with a `schedule-broken` issue.
- Cron: a fire time in a DST spring gap was not moved to the next valid instant when another transition lay between the search start and the gap, for example `30 2 29 3 *` in Europe/Berlin searched from 2025-04-01; it now fires at 2026-03-29T01:00:00Z. The cache of parsed expressions is bounded to 256 entries, and expressions that differ only in whitespace share one entry.
- `TaskClient.putSchedule` returned the fire time it computed even when the store kept the existing one; it returns the stored next fire time.
- Resuming a fixed-delay definition that was not paused re-armed it one delay from now, which with `Overlap.ALLOW` and a running occurrence started a second occurrence early. Resuming a definition that is not paused now changes nothing, in one store call.
- An operator trigger kept the record of the occurrence in flight, so when that task ended, its re-arm overwrote the triggered fire time or its death paused the definition. A trigger now forgets the occurrence.
- All stores: a recurring commit whose occurrence id belongs to an existing task now writes nothing and reports false; PostgreSQL and Redis used to advance the definition, and a fixed-delay definition adopted the unrelated task.
- Redis: one task hash with an unreadable due time, revision, keep window or state no longer stops a script halfway. Promotion stopped for every queue and left the tasks it had already promoted in no queue; expiry and the end of a task with an unreadable keep window left tasks in the wrong index; delete failed on an unreadable state. An unreadable due time is promoted as due now, an unreadable revision restarts at 1, and an unreadable keep window counts as none. A leased task whose revision cannot be read gets revision 0 from lease reclaim and is ended by the next one, instead of staying leased for good.
- PostgreSQL: a transaction that committed no longer reports a failure when switching the connection back to auto-commit fails afterwards.
- `start()` reads the store information before it starts any service and starts the task processor last, after checking for a `stop()` that gave up waiting, so a start that fails or is stopped meanwhile never leaves claimed tasks without lease renewal, and a stopped runner never starts services afterwards.
- `Misfire.catchUp` also creates the missed fires that are late by less than the misfire threshold, which it used to skip, and a very large `maxFires` no longer allocates a window of that size (an `OutOfMemoryError` stopped the recurring service at about `catchUp(1_000_000_000)`).
- Redis: a claim expired a queued task whose start-by had passed by itself, so the observer never received `TaskEvent.Expired` for it. It now leaves the task for maintenance, as the other stores do.
- PostgreSQL: a failure of any kind, an `Error` too, rolls back the store transaction; before, restoring auto-commit committed the half-done transaction (for example a task SUCCEEDED without its schedule effect).
- PostgreSQL: `putRecurring` locks the schedule row before it checks the occurrence in flight, so a re-put during an occurrence commit no longer forgets that occurrence and its pause on DEAD.
- PostgreSQL: `init` on tables of the current schema version runs no DDL, so starting a runner no longer takes a table lock behind long transactions, and a role with only data privileges can start one.
- PostgreSQL: concurrent batch enqueues that share new unique keys in a different order no longer deadlock.
- PostgreSQL: purge no longer re-reads, on every batch, tasks whose key window is still open.
- `InMemoryStore` purged a finished task only when it was older than its retention, while Redis and PostgreSQL purge it once it is as old; it now matches them. It also no longer keeps the payload of a dead task that only waits for its key window.
- `MutableClock.withZone` ignored the zone; it returns a clock in that zone that follows the original.
- Admin HTTP: the queue filter and queue pause accept every queue in the store registry and reject unknown names without registering them (400 in the filter, 404 on pause and resume); validation errors, such as a cancel reason over 512 characters, are answered 400 instead of 500. The login throttle checks and records each attempt atomically per address, so concurrent attempts no longer get past a block, and at its cap evicts the oldest addresses instead of clearing all of them. Sessions stay within their cap under concurrent logins, and one user has at most 20, so a user logging in over and over ends their own oldest sessions instead of other users'. A successful login no longer clears the failed logins counted for its address, so an attacker with one valid account can no longer reset the block between guesses at another; at its cap the throttle keeps active blocks. The session cookie's `Max-Age` is renewed with every authenticated response, so the browser keeps the cookie as long as the server keeps the session. The error log of a 500 answer no longer contains the raw request path, which could hold a unique key.
- Micrometer: a concurrency-limit supplier that throws no longer stops the gauge refresh.
- Dashboard: Trigger is disabled for a paused schedule, which does not fire, and its confirmation says that the task is created on the runner's next scheduling round.

## [4.0.0] - 2026-11-05

### Changed (breaking)

- Internal classes are no longer public: the whole `service` package (`DefaultAdminOps`, `IdAllocator`, `Names`, `TaskProcessorService` and the rest) is gone from the public API and its classes are package-private in `today.bonfire.oss.bth4j`, as are `CustomThread` and `QueuesHolder`, and the `TaskClient` accessors `store()`, `names()`, `codecs()`, `ids()`, `queues()` and `clock()`. `Codecs` stays public and moves to `today.bonfire.oss.bth4j` (see Added). The loggers of the moved classes keep class-based names, now under `today.bonfire.oss.bth4j` (for example `today.bonfire.oss.bth4j.TaskExecution`, was `today.bonfire.oss.bth4j.service.TaskExecution`); see `Loggers`. The `Misfires` helpers are now `RecurringDefinition.misfireCode`, `misfireMaxFires` and `misfire(String, int)`. `Json` stays public but is documented as internal.
- `EnqueueFailedException.id()` throws `NoSuchElementException` when `ids()` is empty; check `ids()` before reading the first id.
- Redis layout 3. The Redis store needs Redis 7.4 or newer or Valkey 9 or newer, and refuses a namespace written by 3.0 (`init` checks the layout version in `meta`; there is no migration, start with a new namespace). The task hash keeps only short fields so that it stays a listpack: the payload moves to `d:<id>`, the steps to `st:<id>` and the failures to the list `f:<id>` (about half the memory per task with a 300-byte payload). SCHEDULED tasks are in one zset per queue (`sched:<qid>`), the counts are the cardinalities of the state zsets (the `c:<qid>` counters are gone and cannot drift), and the key fields of a finished task expire with the key itself through hash field expiry (the `keys` zset and the RELEASE_KEYS script are gone; `releaseKeys` returns 0 on Redis).
- `ExecutionStore` has a new abstract method `finishCancelledExpired`; custom stores must implement it (see Fixed).
- `InspectionStore` has a new abstract method `idHighWaterMark()`, the first task id not yet allocated; custom stores must implement it (Redis: the id counter plus one, PostgreSQL: the task id sequence, in-memory: the next id).
- `StoreInfo.schemaVersion` is per store and `StoreInfo.SCHEMA_VERSION` is gone: the Redis store reports `RedisTaskStore.LAYOUT_VERSION` (3), the PostgreSQL store `PostgresTaskStore.SCHEMA_VERSION` (2) and the in-memory store 1.
- PostgreSQL schema 2. `init` refuses tables written by 3.0 (schema version 1) before it changes anything; there is no migration, use a new prefix or drop the tables. Schema 2 adds the column `occurrence_id` to `<prefix>_schedule` (see Fixed), and `schemaStatements()` no longer contains an `ALTER TABLE`.
- `TaskEvent.Outcome` has a third value, `UNKNOWN`: a store call that throws (a timeout, a lost reply) is reported as `UNKNOWN` instead of `LOST`, so a committed acknowledgement whose reply was lost no longer looks like a lease loss. `LOST` now means only that the store rejected the transition. The `bth4j.tasks` metric gains the outcome tag value `unknown`. An exhaustive `switch` over `Outcome` must add the case.
- `AdminOps.retry` and `AdminStore.retry` return the new enum `RetryOutcome` (`RETRIED`, `STALE`, `DUPLICATE`) instead of a boolean; callers and custom implementations must adapt (see Fixed).
- The SPI default overloads that only delegated with a null `ScheduleEffect` are removed: `ExecutionStore.ack(id, revision, keep, keepPayload)`, `fail(id, revision, failure, retryAt, keepDead)`, `failExpired(id, revision, failure, retryAt, keepDead)`, `finishCancelled(id, revision, reason, keepPayload)` and `finishCancelledExpired(id, revision, reason, keepPayload)`, `AdminStore.cancel(id, revision, reason)` and `delete(id, revision)`, and `ScheduleStore.putRecurring(definition, nextFire)`. Pass the effect (null for none) to the full forms, and `putRecurring(definition, nextFire, keepUntil)` with `keepUntil = nextFire` for the old meaning. Custom stores and decorators have only the full forms to implement.
- The `afterId` task listing is removed: `TaskClient.tasks(state, queue, afterId, limit)`, `AdminOps.tasks(state, queue, afterId, limit)` and `InspectionStore.tasks(state, queueId, afterId, limit)` are gone, and the cursor form is the only listing (`tasks(state, queue, cursor, limit)` returning a `TaskViewPage`, `TaskPage` on the store; pass a null cursor for the first page). Admin HTTP `GET /api/v1/tasks` always answers `{"items": [...], "next": ...}`: the `after` parameter and the bare JSON array reply are gone, and a missing `cursor` means the first page, like an empty one. Hosts that implement or fake `AdminOps` or `InspectionStore` drop the method.
- `maxRun` is renamed `maxRunTime`, because it is a duration, not a count like `maxAttempts`: `TaskRequest.Builder.maxRunTime(Duration)`, `TaskRequest.maxRunTime()`, `TaskView.maxRunTime()`, `TaskRecord.maxRunTime()` and its builder method, and the admin HTTP task field `maxRunTime`. Storage keeps `max_run_ms` (PostgreSQL) and `mr` (Redis).
- Every attempt now has a maximum run time. A task or schedule without its own `maxRunTime` gets the runner's new `defaultMaxRunTime`, one hour by default (`BackgroundRunner.Builder.defaultMaxRunTime(Duration)`). A task that legitimately runs longer needs its own `maxRunTime` or a larger default. At the limit the attempt gets a cancel request as before. If it is still running one lease-renewal period later, the runner stops renewing its lease (see Added).
- `TaskRequest.Builder.maxRunTime` and `ScheduleDefinition.maxRunTime` accept at most `TaskRequest.MAX_RUN_TIME` (about 24.8 days, `Integer.MAX_VALUE` milliseconds). The PostgreSQL store keeps `maxRunTime` as an int of milliseconds, so a longer value used to fail at enqueue with an `ArithmeticException`; it is now a `TaskValidationException`.
- `ScheduleStore.putRecurring` returns the new enum `PutRecurringOutcome` (`CREATED`, `CHANGED`, `UNCHANGED`) from the same atomic call. A put that would write nothing keeps the revision instead of taking a new one: every field is stored already, the next fire time is kept, and no finished occurrence is recorded as in flight. A runner re-registering its schedules at start therefore no longer makes a concurrent commit of another runner fail its revision check. Custom stores must return the outcome; the paused flag of an existing definition is not compared.
- Records with a new component: `ScheduleDefinition` has `maxRunTime` after `maxAttempts`, `RecurringDefinition` has `maxRunTimeMs` after `maxAttempts`, `ScheduleView` ends with `maxRunTime`, and `RunnerHealth` has `abandonedAttempts` after `runningTasks`. Code that calls the canonical constructors adds the argument.
- `TaskRescheduleException`, `TaskUnrecoverableException`, `TaskLeaseLostException` and `TaskCancelledException` are `final` and extend the new sealed `TaskSignal`, so one `catch (TaskSignal s)` lets the runner's control flow through a processor's own `catch (RuntimeException e)`. Removed as unused: `OperationNotAllowed`, `common.Random`, `common.Errors`, and the byte-array methods of `JsonMapper`, which now has only `fromJson(String, Class)` and `toJson(Object)`.
- API renames for consistent names (storage, Redis keys and PostgreSQL tables and columns are unchanged). "event" meaning the task type becomes "type": `TaskView.type()`, `ScheduleView.type`, `TaskEvent.Deferred.type`, `AdminOps.typeNames()`, `TaskStore.typeId(String)` and `typeNames()`, `typeId` in `TaskRecord` (and its builder), `RecurringDefinition` and `ExpiredLease`, `ClaimRequest.knownTypeIds`; the issue kind `unknown-event` is `unknown-type`; the admin HTTP field `event` is `type`; the Micrometer tag `event` is `type` on `bth4j.tasks`, `bth4j.task.duration` and `bth4j.deferred`; the log MDC key `bth4j.event` is `bth4j.type`. The encoded payload text is `encodedPayload`: `TaskView.encodedPayload()`, the `TaskRecord` component and builder method, and `RecurringDefinition.encodedPayload`. Instants get an `At` suffix: `TaskRecord` and `TaskView` `created` and `stateChanged` are `createdAt` and `stateChangedAt` (components, builder methods, accessors), and the admin HTTP task fields `created` and `stateChanged` are `createdAt` and `stateChangedAt`. `EnqueueFailedException.stored()` is `storedCount()`. `Misfire.CatchUp(int max)` and `Misfire.catchUp(int max)` take `maxFires` (accessor `maxFires()`), and `RecurringDefinition.catchUpMax` is `catchUpMaxFires`. `exceptions/TaskConfigurationError` is `TaskConfigurationException`, and `TaskErrorException` is removed: an unknown queue now throws `TaskValidationException`. `DefaultVtExecutor.getCurrentMaxThreads()` and `getAvailablePermits()` are `currentMaxThreads()` and `availablePermits()`. `ScheduleView` uses the definition's types: `zone` is a `ZoneId` (null when none is stored), `misfire` is a `Misfire`, and `overlapSkip` is `overlap` of type `Overlap`. The admin HTTP schedule fields keep `zone` and `misfire` as text, add `catchUpMaxFires` (only for `CATCH_UP`) and replace `overlapSkip` with `overlap` (`ALLOW` or `SKIP`). `RunnerHealth.running` and `abandoned` are `runningTasks` and `abandonedAttempts`, and so are the admin HTTP health fields; the Micrometer gauge names are unchanged.

### Added

- `BackgroundRunner.builder().failureDetail(FailureDetail.CLASS_NAME_ONLY)` for hosts whose exception messages may carry customer data: the stored failure, the `TaskEvent` error (a `RedactedFailure`), the issues and the runner's log lines then keep the exception class name, the attempt and the time, and no message or stack. `FailureDetail.FULL` is the default and unchanged.

- Cursor listing of tasks: `InspectionStore.tasks(state, queueId, cursor, limit)` returns a `TaskPage(items, next)`, `TaskClient.tasks` and `AdminOps.tasks` have the same form returning a `TaskViewPage`. The cursor is an opaque position in the listing that each store encodes itself (PostgreSQL `<state_changed in epoch microseconds>:<id>`, Redis `<zset score>:<id>`, in-memory `<state_changed in epoch nanoseconds>:<id>`), `next` is null after the last page and a malformed cursor throws `IllegalArgumentException`. Custom `InspectionStore` implementations must add the method. `AdminOps.tasks(state, queue, cursor, limit)` is a new abstract method on a public interface: hosts that implement or fake `AdminOps` must add it.
- Admin HTTP `GET /api/v1/tasks` answers `{"items": [...], "next": ...}` (an empty or missing `cursor` is the first page; see Changed (breaking)). The dashboard's Tasks page pages with `next`.

- Lookup and cancel by unique key. `InspectionStore.taskByKey(key)` returns the task that holds the key now: an open task, or a finished one inside its `keepFor` window; empty when none does (Redis: one GET of `k:<key>` and the task read; PostgreSQL: one lookup through the unique index on `unique_key`, ignoring a key whose `key_until` has passed; in-memory: the same rule). It is a new abstract method: custom stores must implement it. `TaskClient.taskByKey(key)` and `AdminOps.taskByKey(key)` return an `Optional<TaskView>`, and `AdminOps.cancelByKey(key, reason)` cancels the holder with the revision it read and returns the outcome of `cancel`, or the new `CancelOutcome.NOT_FOUND` (no task holds the key) or `CancelOutcome.FINISHED` (the holder already ended and only keeps the key for its window); `STALE` means it changed between the read and the cancel. Hosts that switch exhaustively on `CancelOutcome` must add the two values. Cancelling a waiting fixed-delay occurrence by key pauses its schedule, as cancel by id does. `AdminOps.taskByKey` and `AdminOps.cancelByKey` are new abstract methods: hosts that implement or fake `AdminOps` must add them.
- Admin HTTP `GET /api/v1/tasks/by-key/{key}` (404 when no task holds the key) and `POST /api/v1/tasks/by-key/{key}/cancel` (body `{"reason"}`, no revision; 400 for a blank or over-long key, 404 when no task holds the key, 409 when the holder is already finished or changed meanwhile). The dashboard's Tasks page has a "Find by key" box that opens the holder's task page.

- An attempt that ignores its cancel request is abandoned one lease-renewal period after its maximum run time. Its lease is no longer renewed, so it lapses and maintenance retries or ends the task. Its thread keeps its executor and queue slots until the processor returns. The runner raises the issue `attempt-abandoned` once per attempt; the detail says how many abandoned attempts hold slots. `RunnerHealth.abandonedAttempts`, `BackgroundRunner.abandonedAttempts()`, the gauge `bth4j.runner.abandoned` and the admin health field `abandonedAttempts` count them.
- `ScheduleDefinition.maxRunTime(Duration)` gives each occurrence's attempts a maximum run time. It is stored with the definition (Redis hash field `mr` of `cron:<id>`, PostgreSQL column `max_run_ms` of `<prefix>_schedule`) and shown as `ScheduleView.maxRunTime` and the admin field `maxRunTime`.
- `TaskRequest.MAX_ATTEMPTS` names the largest `maxAttempts` (32767); `TaskRequest.MAX_RUN_TIME` the largest `maxRunTime`.
- `Codecs` (`new Codecs(jsonMapper)`) encodes and decodes payloads and step results exactly as the runner stores them, so a test can pin their stored form without copying the rules.
- `Loggers` names every logger the runner writes to (`RUNNER`, `CLIENT`, `PROCESSOR`, `ATTEMPT`, `MAINTENANCE`, `RECURRING`, `PROMOTION`, `EXECUTOR`, `OBSERVERS`, `TASKS`), and `ROOT` is the prefix all of them except `TASKS` share. The names are class-based and stay fixed when an internal class moves, so log configuration and log capture by name keep working.

### Changed

- `TaskType.interruptOnCancel()` also interrupts a running processor when lease renewal reports a lost lease. Only an attempt actually interrupted for lease loss has its outcome discarded; otherwise completion and failure still go through the store's revision fence and can be applied before takeover. The interrupt is cleared before the thread is reused. Types that did not opt in still learn of lease loss at their next check; unique keys protect task records, so side effects must be fenced or idempotent.
- The Redis scripts collect their zset writes per key and send one variadic command per key at the end of the call, read the task hash with one HMGET and write it with one HSET per task, and compute the revision and the attempt count in Lua: a claim of 32 tasks costs about a third of the commands it did. ENQUEUE receives the queue id, the start-by time and the payload as arguments instead of reading them back, and takes a free unique key with one `SET NX GET`. FAIL appends the new failure in the script instead of reading, extending and rewriting the list from the client. PURGE reads at most max(4 x limit, 1000) entries of tasks whose key window has passed per call, and none whose window is still open.
- Redis: PROMOTE reads each queue's head first (an idle poll costs one command per queue plus two instead of two per queue), CLAIM reads `st:` and `f:` only for tasks that have them, FAIL trims the failure list only when it grew past 20, `renew` sends leases in chunks of 256 in one pipeline, `purgeWorkers` removes at most 500 workers per script call and loops, and a pipelined batch after `SCRIPT FLUSH` loads the script once and resends only the rejected calls.
- `TaskClient.enqueueAll` reserves the ids of a batch with one store call (`IdAllocator.nextIds`); the block end is overflow-checked.
- Redis `heartbeat` no longer mistakes a second heartbeat in the same millisecond for a removed worker; a duplicate unique key reports the holder id as text, so ids above 2^53 are exact.
- `ThroughputContract` (in `bth4j-store-tests`) times confirmed acknowledgements (`Succeeded` with `APPLIED`) instead of processor callbacks, checks every accepted id once in both, and reports batch-enqueue-to-start percentiles; `bth4j.benchmark.tasks`, `.warmups` and `.rounds` set the workload.
- The integration tests run against Redis 8.8 and PostgreSQL 18 (images `redis:8.8-alpine` and `postgres:18-alpine`), and against Valkey 9.1.3 with the Maven profile `valkey`; the images are the properties `bth4j.redis.image` and `bth4j.postgres.image`.
- `TaskClient.putSchedule` logs at INFO only when it created or changed a definition, and at DEBUG when the definition was registered already, so a runner start that re-registers its schedules is quiet.

### Fixed

- Redis enqueue stores a random per-call, per-record write token in task hash field `wt`, in the existing HSET. A transport resend with the same token returns stored before checking the unique key, avoiding a second task or a duplicate-key answer for its own write; another token still returns exists.
- Attempts discarded after a lease-loss interrupt emit `Retrying` with outcome `LOST`, as on a fenced failure, without changing the stored task. Interrupts can close sockets and NIO channels, including pooled database or Redis connections used by a processor on a virtual thread.
- An operator retry inside a unique key's `keepFor` window retains the key without expiry while the task is open, so a same-key enqueue returns `Duplicate` and `taskByKey` still finds it. The keep window starts afresh when the task finishes. If another task holds the retained key, retry returns `DUPLICATE` and changes nothing; the admin HTTP route answers 409 with `code: "KEY_HELD"` next to the error message; the dashboard matches this code. A key already released at completion or after its window is not restored: the retry runs without a key, and an enqueue with that key can start a second task.
- Caller-supplied task ids are checked against the allocation high-water mark and stored content (type, queue, encoded payload when retained, and unique key when the stored task still holds one, including after an operator retry). A mismatch throws `TaskIdReusedException`. `enqueueAll` checks the mark before reserving fresh ids, rejects duplicate caller ids and caller ids inside the fresh range, and compares all caller ids before writing. Requests without caller ids incur no extra reads; caller ids below the end of this client's own allocated block skip the high-water read. Headers, account, attempts, retry policy, start-by, max run time, delay, `at(...)`, `keepFor` duration and payload version are not compared. `prepare()` plus a store's own enqueue skips these caller-id checks. Retries must use the same request, encoded identically; a dropped payload cannot be compared. Redis counter rollback can make an allocated id appear unallocated. PostgreSQL uses `pg_sequence_last_value` (PostgreSQL 10+), requiring only USAGE on the sequence.
- Failed batches expose `EnqueueFailedException.notStored()` with zero-based generated-id positions known not to have been written, including collisions and unattempted chunks. `retryRequests(requests)` preserves ids for uncertain writes and caller-set ids, and leaves known unwritten requests without an id; `TaskRequest.withId(long)` copies a request with an id. Never reuse `ids()` entries at `notStored()` positions, which may belong to other tasks. Generated-id collisions abandon the client's current block and retry from a fresh store block, at most three writes; on exhaustion the colliding positions stay in `notStored()` and no replacement ids are reserved. Batch retries preserve request order and encoded records. Concurrent caller-id reuse after preflight is wrapped in `EnqueueFailedException` and still requires caller correction.
- Id reservation, high-water reads and cold queue/event lookups now throw `EnqueueFailedException` on store failure. Empty `ids()` means nothing was written by this call: resend the same requests unchanged, retaining any caller-set ids. Batch failures before initial reservation completes carry empty ids; later failures carry every request's last assigned id in order, with `notStored()` identifying ids not to reuse. Single `enqueue` retains a caller id even on high-water-read failure, and carries a generated id only once its write was attempted.
- The dashboard ships its Vue runtime (`dashboard/vendor/vue.global.prod.js`, 3.5.13) instead of loading it from a CDN, and the admin HTTP Content-Security-Policy no longer allows `cdn.jsdelivr.net` as a script source, so a compromised CDN cannot run code in an operator's session and the dashboard works without internet access.
- Paging the task listing with `afterId` re-read the cursor task, so a task that left the listed state between pages broke the walk: PostgreSQL ended the listing silently (the task's new `state_changed` is later than every listed row) and Redis restarted from the beginning and repeated tasks. The cursor form (see Added) does not depend on the last task of the previous page and has neither case; a task whose own position moves during the walk can still be seen twice or missed. The `afterId` form is removed (see Changed (breaking)).
- PostgreSQL `allocateIds(1)` took its id with a bare `nextval`, outside the lock that keeps a block allocation contiguous, so it could land inside the range of a concurrent block and two tasks got the same id (the second enqueue reported as accepted and the task was lost). Every count now takes the lock, so single-id allocation is serialised with block allocation and needs the UPDATE privilege on the `meta` table, as block allocation already did.
- Redis `tasks` paging repeated pages without end when a task of an unknown event had been deferred: the cursor was the task's `due` field, but the deferral re-scores it in the queue zset. The cursor is now the score the task has in the zset being paged.
- Redis `purge` could remove nothing for as long as tasks with an open key window sat in front of purgeable ones, because it paged past them on every call. Tasks with a key window are now kept in `hold:<state>:<qid>` (scored by `keyUntil`) instead of `rm:<state>:<qid>`, the zset purge reads, and purge drains `hold` when the window has passed. The layout has these two zsets and the task hash fields `hs` and `fc`, which say whether `st:<id>` and `f:<id>` exist, so that a claim reads those keys only when they do. A namespace written by an earlier 4.0.0 snapshot has layout 2 and is refused by `init`, because it lacks them and a claim would skip its steps and failures.
- `renew` no longer extends a lease that has already expired (Redis and PostgreSQL; the in-memory store follows): the task is reported as not owned and left for the maintenance sweeper. Before, a worker whose renewal came after the expiry but before the sweeper acted kept the lease with an unchanged revision, and the sweeper then ended a cancel-requested task as CANCELLED while the processor was still running, which freed its unique key for a second task.
- The sweeper ends an expired lease of a cancel-requested task with the new `ExecutionStore.finishCancelledExpired`, which does nothing when the lease is no longer expired, like `failExpired`. The worker's own `finishCancelled` is unchanged. Custom `ExecutionStore` implementations must add the method.
- Queue concurrency limits (`QueuePolicy.maxConcurrent`) could lose slots for good: each processor kept its own per-queue counts, so a processor restarted after its thread died counted the inherited tasks but never released them, and a task reclaimed by the same worker while its earlier attempt was still finishing replaced that attempt's entry, so the earlier attempt's slot was never released. The counts now have one owner per runner, shared across processor restarts, and every attempt releases its slot exactly once.
- A lapsed lease can no longer be revived, so `leaseDuration` must sit well above the worst pause of a worker (GC, container freeze, slow store round trip); the minimum of 1 s makes leases of a few seconds fragile.
- An `Error` thrown by a processor is now recorded as a failure and goes through the retry policy, instead of leaving the task leased until its lease expires. `OutOfMemoryError` and other `VirtualMachineError`s (except `StackOverflowError`) are rethrown after being recorded, so the thread's uncaught exception handler still sees them (with their message and stack, which `failureDetail` does not cover). Errors thrown by a retry policy, the store, an observer or the schedule update no longer escape before the task is recorded either. The rethrow of a fatal Error applies to task execution only; in maintenance and the scheduler an Error from an observer or a retry policy is logged and swallowed.
- A fixed-delay schedule could stay parked forever: its next fire time is parked 100 years ahead when the occurrence is created and was set again after the ack in a second call, so a process death or store error between the two left the definition parked, neither paused nor reported. The re-arm after a succeeded occurrence, and the pause after one that ends DEAD, CANCELLED or with an expired lease, now happen in the same atomic step as the transition: `ExecutionStore.ack`, `fail`, `failExpired`, `finishCancelled` and `finishCancelledExpired` take an optional `ScheduleEffect`. The store records the in-flight occurrence of a fixed-delay definition (Redis hash field `occ` in `cron:<id>`, PostgreSQL column `occurrence_id` in `<prefix>_schedule`) and applies the effect only while that id is the finishing task. A re-registration with unchanged timing during the occurrence keeps its re-arm and starts no second occurrence, and neither does a trigger under `Overlap.SKIP` (the commit finds the key held, parks the definition, and the running occurrence re-arms it). Without overlap protection a trigger starts a second occurrence while the first runs; the newer one then owns the re-arm. A stale effect of a replaced or deleted definition does nothing. `AdminStore.cancel` and `delete` take the same optional `ScheduleEffect`, so cancelling or deleting a waiting fixed-delay occurrence pauses its definition atomically (and only when that occurrence is the recorded one). `ScheduleEffect.applied()` reports whether the store changed the definition; the `schedule-paused` issue is raised only then. `AdminOps.pauseSchedule(id, false)` re-arms a fixed-delay definition while it is still paused and resumes it afterwards.
- The runner's misfire advance (`SKIP` and `CATCH_UP`) carries the definition revision and the fire time it read and does nothing when either changed or the definition is paused, so a stale advance can no longer move a freshly registered schedule far into the future or overwrite what another runner wrote. `ScheduleStore.setNextFire(id, revision, expectedFire, next)` is the fenced write; `setNextFire(id, next)` (the operator's trigger and resume) now assigns a new revision.
- `TaskClient.putSchedule` recovers a definition whose stored next fire time was parked or pushed out: the stored time is kept while a fixed-delay occurrence is still running, or while it is not later than the second fire after now (`now + delay` for a fixed delay), otherwise it is recomputed. `ScheduleStore.putRecurring` takes that bound as `keepUntil`.

## [3.0.0] - 2026-10-31

3.0 is a redesign of 2.x: a new public API, a new coordination protocol and a storage interface with Redis,
PostgreSQL and in-memory implementations. 3.0 cannot read 2.x data: drain the 2.x queues before upgrading,
or start 3.0 with a new Redis namespace. Requires Java 21, and Redis 7.0 or newer or PostgreSQL 9.5 or
newer, depending on the store. See `docs/design-3.0.md`.

### Changed (breaking)

- The single `bth4j` artifact is split into `bth4j-core`, `bth4j-redis` and `bth4j-postgres`, with `bth4j-testing` for tests. Applications depend on `bth4j-core` and one store module.
- Task types: `Event` (and the `eventParser` setting) is replaced by `TaskType<T>`, declared once per kind of task with `TaskType.of(name, PayloadClass.class)`, `TaskType.of(name, PayloadCodec)` or `TaskType.of(name)` and `payloadVersion(n)`. The same constant is used to enqueue and to register the processor.
- Producers: `TaskOps` is replaced by `TaskClient`, reached with `BackgroundRunner.client()` or built on its own with `TaskClient.builder()`. `Task` and `Task.Builder` are replaced by the immutable `TaskRequest` (queue, account, `at`, `delay`, `uniqueKey`, `maxAttempts`, headers, `id`, plus `startBy`, `maxRun` and `retryPolicy`). `enqueue` returns `EnqueueResult.Accepted` or `Duplicate` instead of a boolean, and throws `EnqueueFailedException` (carrying the id to retry with) when the store cannot be reached. Recurring definitions are `ScheduleDefinition` with `putSchedule`, `deleteSchedule` and `schedules`.
- Processors: `TaskProcessor<T>` is a functional interface `process(TaskContext, T)`; `dataTypeClass()` is gone. `TaskContext` gives the task, id, attempt, headers, clock, `progress`, `step` and the cancel flag. `TaskCallbacks` and `taskHandlerDecorators` / `recurringTaskHandlerDecorators` are replaced by `TaskObserver` and the sealed `TaskEvent` (`Started`, `Succeeded`, `Retrying`, `Died`, `Rescheduled`, `Cancelled`, `Expired`, `LeaseExpired`, `Deferred`, `ScheduleFired`, `Purged`).
- Task ids are 64-bit numbers allocated by the client in blocks (`TaskClient.nextId()`, `idBlockSize`); the text ids with the `|` separator and the pipe-separated task string are gone. Queue names and task type names are stored as numeric ids from registries in the store, and there are no foreign keys.
- The coordination protocol is lease and revision based. Every state change is one atomic store call that checks the task's `revision` (the fence); a worker that lost its lease cannot complete, fail, reschedule or checkpoint the task. The stale-task timeout, the lock-based maintenance and the lease token are gone: `leaseDuration` replaces `staleTaskTimeout`, and an expired lease is retried by `failExpired`, which also leaves a lease alone that was renewed after the expiry scan.
- Task states are QUEUED, SCHEDULED, LEASED, SUCCEEDED, DEAD, CANCELLED and EXPIRED. Succeeded tasks are kept (10 minutes by default) instead of removed, dead tasks are kept 90 days by default, and a retention of zero removes the record at the transition. A task ends CANCELLED when an operator cancels it, when its processor throws `TaskCancelledException` or when it runs past `maxRun`, and EXPIRED when its `startBy` passes before it started; both are kept for `cancelledRetention` (48 hours by default).
- Failures are recorded on the task (the last 20, with type, message and stack). Retries follow a `RetryPolicy` (exponential backoff with jitter by default) instead of `taskRetryDelay` and `Event.retryCount()`; the attempts are `maxAttempts` per request, `defaultMaxAttempts` (10) otherwise.
- `BackgroundRunner`: `BackgroundRunner.builder()` replaces `new BackgroundRunner.Builder()`, `start()` replaces `run()` and `stop()` replaces `stopRunner()`; new `quiet()`, `resume()`, `registry()`, `client()` and `workerId()`. The builder takes `store(FullStore)` instead of `jedisClient` and `namespacePrefix`, `concurrency(Concurrency)` instead of choosing an executor, and its settings were renamed or added: `idlePollInterval` replaces `taskProcessorQueueCheckInterval`, `scheduledTasksCheckInterval` replaces `delayedTasksQueueCheckInterval`, `serviceCheckInterval` replaces `BGThreadCheckInterval`, `succeededRetention`, `deadRetention`, `cancelledRetention`, `keepSucceededPayload`, `purgeInterval`, `purgeBatchSize`, `claimBatchSize`, `idBlockSize`, `defaultMaxAttempts`, `workerLabel`, `observer`, `retryPolicy`, `clock`, plus `retryPolicy(name, policy)`, `queue(name, QueuePolicy)` and `workerStaleAfter`. `cronLockDuration` and `recurringTasksQueueAheadDuration` are gone; occurrences are created when they come due.
- Concurrency: the default is a fixed limit of twice the number of processors on virtual threads; `Concurrency.adaptive(min, max)` keeps the adaptive limit. `DefaultPtExecutor` is removed. `BackgroundExecutor` has the contract `reserve(max, wait)`, `release(n)`, `execute`, `activeCount`, `shutdown`, `awaitTermination`; `isPoolFull` and `getExecutor` are gone.
- Unknown task types: a runner claims only the types it has processors for (PostgreSQL filters in the claim query, Redis defers them 5 seconds without an attempt, the in-memory store skips them).
- Recurring definitions: each fire time creates one task exactly once across instances (the commit compares the definition revision and the fire time); missed fire times are skipped; re-registering with the same expression keeps the next fire time; definition revisions come from a counter that never resets.
- `stop()` waits for services and running tasks up to `shutdownTimeout` (default 30 seconds), keeps renewing the leases of running tasks meanwhile, and shuts down the task executor.
- The Redis key layout lives in `bth4j-redis` (`THC` is gone). All keys carry the namespace as a hash tag, so the store works on Redis Cluster, and every transition is one Lua script that reads Redis time.
- `QueuesHolder` holds logical queue names; the default queues are `Q:DEF`, `Q:LOW`, `Q:MED` and `Q:HIGH` with `Q:DEF` as default.

### Added

- `bth4j-core`: `TaskType`, `PayloadCodec`, `TaskRequest`, `Uniqueness`, `EnqueueResult`, `TaskClient`, `TaskProcessor`, `TaskContext`, `TaskView`, `TaskProcessorRegistry`, `RetryPolicy`, `TaskObserver`, `TaskEvent`, `Concurrency`, `ScheduleDefinition`, and the store SPI in `today.bonfire.oss.bth4j.spi` (`TaskStore`, `ExecutionStore`, `MaintenanceStore`, `ScheduleStore`, `InspectionStore`, `FullStore`, `TaskRecord`, `TaskState`).
- `bth4j-redis`: `RedisTaskStore(UnifiedJedis, namespace)`: one hash per task with only the fields that are set, sorted sets for queues and state indexes, one Lua script per transition. Requires Redis 7.0 or newer because the scripts read the clock before writing (effect replication).
- `bth4j-postgres`: `PostgresTaskStore(DataSource, prefix)`: tables `<prefix>_task`, `_queue`, `_event`, `_worker`, `_schedule` and `_meta`, partial indexes per state, claims with one bounded index scan per queue under `FOR UPDATE SKIP LOCKED`, revision-checked `UPDATE` statements. `init()` creates the schema under an advisory lock and `schemaStatements()` provides the DDL for migration tools. Uses only `java.sql`. The SQL uses `FOR UPDATE SKIP LOCKED` and `ON CONFLICT`, so PostgreSQL 9.5 or newer is required; it is tested on 17.
- `bth4j-testing`: `InMemoryStore` and `MutableClock` for tests of applications.
- `bth4j-store-tests`: `StoreContract`, the tests every store must pass; all three stores run it. Not published.
- Steps: `TaskContext.step(name, ...)` stores the result of each step durably, so a retry resumes after the last completed step. At least once per step; side effects belong inside steps.
- Unique keys with a keep window (`Uniqueness.keepFor(duration)`), enforced by a partial unique index in PostgreSQL and a key string in Redis.
- Client-allocated ids and safe enqueue retries after a lost reply (`TaskClient.nextId()`, `TaskRequest.Builder.id`).
- Progress text for operators (`TaskContext.progress`), account labels and headers on tasks, a worker registry with a label per runner.
- Retention and purge per terminal state, with unique-key release; `quiet()` and `resume()` on the runner.
- Inspection on the client: `task(id)`, `counts()` and `tasks(state, queue, afterId, limit)`.
- Builder settings are validated, and `build()` fails early on a missing store or an invalid queue configuration.
- GitHub Actions workflows for pull request builds, CLA checks and releases, using the shared BonfireTrunk workflows.
- `CHANGELOG.md` and a Contributing section in the README.
- Cancel: `AdminOps.cancel(id, revision, reason)` cancels a QUEUED or SCHEDULED task at once and asks a LEASED task to stop; the runner learns of it when it renews the lease, `TaskContext.cancelRequested()` and `checkCancelled()` show it to the processor, and the task ends CANCELLED with the reason kept on the record. `TaskType.interruptOnCancel()` also interrupts the processor's thread.
- `startBy` is enforced: a QUEUED or SCHEDULED task whose `startBy` passed is never claimed, maintenance moves it to EXPIRED and the runner emits `TaskEvent.Expired`.
- `maxRun` is enforced: a task running longer than `maxRun` gets a cancel request ("max run time ... exceeded") from the lease renewal and ends CANCELLED.
- Named retry policies: `BackgroundRunner.builder().retryPolicy(name, policy)` registers one and `TaskRequest.retryPolicy(name)` picks it; an unknown name uses the default policy and records an issue.
- Queue policies: `BackgroundRunner.builder().queue(name, QueuePolicy)` gives a queue a `weight` for its share of the free slots and a `maxConcurrent` limit on this runner.
- Queue pause and resume: `AdminOps.pauseQueue(queue, paused)` stops every runner from claiming from the queue; tasks can still be enqueued to it.
- Health: `BackgroundRunner.health()` returns a `RunnerHealth`, `issues()` returns the last 100 `Issue`s the runner recorded, and `drain(Duration)` goes quiet and waits for the running tasks.
- Worker registry: runners write a heartbeat (`lastSeen`, `running`) every `maintenanceCheckInterval`, and maintenance deletes workers silent for `workerStaleAfter` (10 minutes by default).
- `AdminOps`, the operator view and operations over one store (counts, queues, tasks, retry, cancel, delete, workers, schedules, health, issues), reached with `BackgroundRunner.admin()` or `TaskClient.admin()`; the SPI has the new `AdminStore` in `FullStore`.
- `TaskClient.prepare(TaskRequest)` returns the validated `TaskRecord`, and `PostgresTaskStore.enqueue(Connection, TaskRecord)` stores it inside the caller's transaction.
- Schedules: fixed-delay definitions (`ScheduleDefinition.every(id, type, payload, delay)`, re-armed when an occurrence succeeds and paused when an occurrence ends dead or cancelled), `zone(ZoneId)` for cron, `misfire(Misfire.SKIP | FIRE_ONCE_NOW | catchUp(max))`, `overlap(Overlap.SKIP)`, and pause, resume and trigger through `AdminOps`.
- `LoggingTaskObserver`: one SLF4J line per `TaskEvent` with `bth4j.task`, `bth4j.event` and `bth4j.queue` in the MDC.
- `bth4j-micrometer`: `MicrometerTaskObserver` (counters `bth4j.tasks`, `bth4j.deferred`, `bth4j.schedule.fired`, `bth4j.purged` and timer `bth4j.task.duration`) and `MicrometerRunnerMetrics.bind` (gauges `bth4j.runner.running`, `bth4j.runner.up` and `bth4j.tasks.state`); `micrometer-core` is a provided dependency.
- `bth4j-admin-http`: `AdminHttpServer`, a JSON admin API over `AdminOps` on the JDK HTTP server with users, roles (`ADMIN`, `VIEWER`), cookie sessions, CSRF tokens, optional CORS and HTTPS, and static file serving.
- `dashboard/`: a Vue 3 operator dashboard without a build step (overview, queues, tasks, dead tasks, schedules, workers, issues), served by `AdminHttpServer.staticDir` or any static host.
- Redis: the keys `paused`, `startby`, `workers` and `crondefs`, the fields `seen` and `running` on `w:<id>`, the fields `zone`, `mf`, `cum`, `fd`, `os` and `paused` on `cron:<id>`, and the scripts CANCEL, FINISH_CANCELLED, RETRY, DELETE, EXPIRE, PURGE_WORKERS, CRON_PAUSE and CRON_SET_NEXT. `reclaim`, `dueRecurring` and `heartbeat` are plain commands (24 scripts in all), and the reverse registry hashes `reg:*:names` and the `queues` set are gone: listings invert `reg:queue` and `reg:event`, purge walks the values of `reg:queue`.
- PostgreSQL: `<prefix>_worker.running`, and `<prefix>_schedule` columns `zone`, `misfire`, `catch_up_max`, `fixed_delay_ms`, `overlap_skip` and `paused` with the partial index `_due (next_fire) WHERE NOT paused`; the schema version stays 1.

### Removed

- `Event`, `Task`, `Task.Builder`, `TaskOps`, `TaskCallbacks`, and the builder settings `jedisClient`, `namespacePrefix`, `eventParser`, `taskHandlerDecorators`, `recurringTaskHandlerDecorators`, `staleTaskTimeout`, `taskRetryDelay`, `cronLockDuration` and `recurringTasksQueueAheadDuration`.
- `DefaultPtExecutor`, `THC`, and the single `bth4j` artifact.
- Text task ids, the pipe-separated task string and the locks of the stale/lock based protocol.
- Reading 2.x data: queues of a 2.x deployment must be drained before upgrading.

### Changed

- Jedis moved to 8.0.2. `JedisPooled` no longer exists in Jedis 8, so `RedisTaskStore` takes a `UnifiedJedis`, for example a `RedisClient` built with `RedisClient.builder()`.
- Parent POM moved to bonfire-oss-parent 2.1.1. All sources are formatted with palantir-java-format through Spotless, which CI enforces.
- Integration tests of the store modules start their own Redis or PostgreSQL with Testcontainers and run under maven-failsafe-plugin in the `integration-test` phase; they need Docker.
- Maven Wrapper upgraded to 3.3.4 with Maven 3.10.0 and a pinned distribution checksum.
- Lombok removed; the library has no annotation processor any more.
