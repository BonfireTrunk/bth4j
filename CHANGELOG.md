and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Adaptive concurrency with CPU and memory targets: `Concurrency.adaptive(min, max, cpuTarget, memoryTarget)` (defaults 0.90 and 0.80 with `adaptive(min, max)`), and `Adaptive.withMemorySignal(MemorySignal.HEAP_AND_SYSTEM)` to count system memory as well as the heap (`MemorySignal.HEAP` is the default).
- `BackgroundExecutor.claimed(reserved, claimed)` tells the executor whether a claim filled its reservation, the demand signal of adaptive concurrency. `BackgroundExecutor.limit()` and `BackgroundRunner.concurrencyLimit()` report the current limit; the Micrometer gauge `bth4j.runner.concurrency.limit` exposes it.
- Workers record the queues and task types they process and whether they accept work (`WorkerInfo.queueIds`, `typeIds`, `accepting`); `quiet()` and `resume()` publish the state with an immediate heartbeat.
- `AdminOps.unservedWork()` (one-minute heartbeat window) and `unservedWork(Duration)` report queued work that no live accepting worker can take: a queue no such worker processes, or a task type none of a queue's such workers registered, with exact counts. Paused queues are skipped. `GET /api/v1/unserved` serves them, the Overview page shows them, and the Workers page lists each worker's queues, types and quiet state.
- `InspectionStore.queuedByType()`: exact QUEUED counts by queue and type.
- `ExecutionStore.ackAll(leases, keep, keepPayload)` acknowledges several tasks without a schedule effect in as few round trips as the store allows; the default calls `ack` for each. The runner sends the acknowledgements of tasks that finish while an earlier batch is on its way as one batch, with no timer and no added delay when it is quiet. Redis runs one script per 256 tasks and PostgreSQL one statement for the batch.
- `BackgroundExecutor.executeWithSlot(SlotTask)` runs a task that may free its slot before it ends. The default keeps the slot until the task ends, as `execute(Runnable)` does; `FixedExecutor` and `DefaultVtExecutor` free it early.

### Changed

- Adaptive concurrency starts at `min` and samples every 500 ms: whole-machine CPU (smoothed) and memory (the lowest reading over 2 s per component, so the GC sawtooth does not count). Growth requires occupied slots at or above the limit, including permit debt, and resource headroom. A full reservation claim provides demand evidence for 5 s and allows one growth step; a partial or empty claim clears it. With fresh evidence growth is about +25 % per step (at most 16 slots) far below the targets, +1 near them; without it, a saturated runner probes by +1 at most once per 5 s under the same resource checks and cooldowns. Free slots prevent growth. CPU above target for 1 s takes 20 % off, memory at target for 1 s takes 25 % off and blocks growth for 5 s, and memory at 95 % drops straight to `min`. Reductions use the highest valid memory component; growth needs every configured component valid. An unavailable signal blocks growth and decays the limit after 5 s. After 30 s without a running task observed at a tick or a nonempty claim, the limit resets to `min`; empty polling does not count as activity. Running tasks are never stopped; a lower limit admits fewer new ones. The throughput heuristics and the fixed 80 % CPU threshold are gone.
- Breaking: `Concurrency.Adaptive` has the components `cpuTarget`, `memoryTarget` and `memorySignal` (the two-argument constructor remains); `Concurrency.adaptive(min, max)` returns `Adaptive`; `FixedExecutor.limit()` returns `OptionalInt`.
- Breaking SPI: `ClaimRequest` takes non-empty, distinct `QueueGrant(queueId, share, cap)` entries instead of queue ids. A store applies the share pass and the refill pass for every queue atomically in one call, honours caps and the total count, and leaves tasks of unknown types untouched, including their due time.
- Breaking SPI: `TaskStore.allocateWorkerId(label, queueIds, typeIds)`, `AdminStore.heartbeat(workerId, running, accepting)` and `InspectionStore.queuedByType()`; `WorkerInfo` adds `accepting`, `queueIds` and `typeIds`; `AdminOps` implementations must add `unservedWork(Duration)`. `GET /api/v1/workers` adds `accepting`, `queues` and `types`.
- `InspectionStore.tasks` (and the task listings of `TaskClient`, `AdminOps` and `GET /api/v1/tasks`) lists QUEUED and SCHEDULED tasks by due time, then id; the other states stay ordered by state change time, then id. Redis already listed waiting tasks by due time; PostgreSQL and the in-memory store now do too, so all stores agree. A cursor taken before the upgrade for those two states may skip or repeat tasks; start the listing again. Custom stores must order the same way.
- Breaking: Redis layout 5. Queued tasks live in one zset per queue and type, `q:<qid>:<tid>`, and `active:<qid>` holds the types whose zset is not empty. A claim intersects that set with the runner's stored type set `ts:<digest>`, so it reads only types that have queued tasks; counts, listings and the exact per-type counts read only those too. Before this, a claim read one zset per known type: with 10,000 registered types and tasks of 4, one Redis measured 690 tasks/s against 9,100 with 10 types, and one idle runner used 11 % of the Redis core. Finished tasks without an open key window are listed, counted and purged from one zset `idx:<state>:<qid>` (the `rm:` zsets are gone); those with one are in `hidx:<state>:<qid>` and `hold:<state>:<qid>`. Enqueue batches run one script per 64 tasks. Type storage names are `seq:type`, `reg:type` and the task hash field `ty`. Worker hashes have the fields `queues`, `types` and `accepting`, and a heartbeat is one script. `init` migrates a namespace written by an earlier 4.1.0 snapshot (layout 4) forward under a lock, after which runners of the older version must not run on it, and refuses one written by 4.0.0 (layout version 3); start those with a new namespace. Later layout changes ship such a migration step too, and `init` refuses a layout newer than the library.
- A task frees its executor slot when its processor returns, before its outcome is written, so the slot takes the next task while the outcome is on its way to the store. The task stays running, with its lease renewed, until the store answers. `FixedExecutor` and `DefaultVtExecutor` let at most twice their current limit run or write their outcome at once, so a slow store still holds back claims; adaptive concurrency counts the slots this bound holds back as occupied. `runningTasks`, `RunnerHealth.runningTasks`, the heartbeat count and `bth4j.runner.running` include tasks whose outcome is still being written, so they can reach twice the limit. Observers of outcome events run after the slot is freed. Queue caps (`maxConcurrent`) still count a task until its outcome is written. A thread waiting in an acknowledgement batch is woken only when its batch returns or when it is to send the next one, not on every batch. Measured on Redis with 50,000 no-op tasks and claim cap 64 (four runs before and after): concurrency 24 about 9,400 -> 14,000 tasks/s, 64 about 16,400 -> 22,200, 128 about 22,700 -> 30,500, 256 unchanged at about 31,000 (claims were already full); at 64 client CPU per task fell from about 65 to 43 microseconds and Redis CPU from about 39 to 33. Tasks that run for milliseconds gain much less, since the slot was held for about 1.5 ms of acknowledgement per task.
- PostgreSQL claims and acknowledgements cost less database work. A claim is one statement (both passes, no transaction round trips) that finds the picked rows by primary key; the known type ids go once per claim, sorted, as a value the planner does not estimate id by id, so a runner with thousands of types no longer plans each claim anew (about 7 ms at 10,000 types) or makes the database sort the ids on every index scan. Batched acknowledgements are one statement per batch instead of one commit per task. Measured on one PostgreSQL 18 container with 20,000 tasks and 64 slots: database CPU per executed task fell from about 660 to 110 microseconds and throughput rose from about 4,300 to 7,500 tasks/s; an idle runner with 10,000 types claims in 0.04 ms instead of 3 to 7 ms.
- Breaking: PostgreSQL schema 3. Task types are stored in `<prefix>_type` with `type_id` columns in tasks and schedules (the storage names were `event` and `event_id`). `<prefix>_worker` has `accepting boolean NOT NULL` and `queue_ids` and `type_ids` as `smallint[] NOT NULL`. The queued index also covers `type_id`. `init` refuses tables written by 4.0.0 (schema version 2) before it changes anything; there is no migration, use a new prefix or drop the tables.

### Fixed

- Redis: a claim by a worker that does not handle a task's type pushed that task 5 s back in the shared queue, which delayed the workers that could run it, repeatedly while the others kept polling. Claims now read only the queues of the worker's types, merged by due time, so foreign tasks are neither touched nor counted against the scan budget.
- Weighted queue claims made up to two store calls per queue, and a failure after the first call left the tasks already claimed to wait for lease expiry. The runner now sends every queue's share in one claim: one script on Redis, one statement on PostgreSQL.
- Queue caps: when a claim found nothing because a queue was at its `QueuePolicy.maxConcurrent`, the runner slept the full `idlePollInterval` (500 ms by default) even after a task of that queue finished. It now claims again as soon as a task of a capped queue finishes, also after the task processor thread was restarted.
- Queue weights whose sum, or whose product with the free slots, exceeded an `int` overflowed when a claim split the slots, so queues got wrong or negative shares. The split now computes in `long`.
- `stop()` publishes at once that the runner accepts no more work (a heartbeat with `accepting` false), so `unservedWork` no longer counts a stopped runner as serving its queues until its heartbeat ages out.
- A maintenance job (lease reclaim, start-by expiry, heartbeat, purge) or the adaptive concurrency sampler that threw an `Error` was never run again, silently; the runner kept reporting the service as running. Each now logs the error and runs again at its next interval.
- A claim whose store returned more tasks than the runner asked for inflated the executor's slots for good. The extra tasks now go back to their queue unrun and the runner raises a `store-error` issue.
- A failed acknowledgement batch made every task in it log the full stack trace and add its own `store-error` issue, so one failure of up to 256 tasks pushed every other issue out. The error is now one issue and one stack trace; the other tasks log one line each.
- Redis: a stored task value that cannot be read (a malformed number, state code or JSON field) or a claim reply of an unexpected shape fails with a `TaskStoreException` naming the task, instead of a raw `NumberFormatException`, `ClassCastException` or `NullPointerException`; the message does not quote stored values.
- Dashboard preview API returns the cursor task-page shape on the first page too.
- A lease renewal round that ran while a finished attempt was still writing its outcome or emitting its events counted that attempt as lost: it logged "N of M leases could not be renewed, those tasks were taken over" and raised a `lease-lost` issue although nothing was taken over. Renewal now ignores such attempts; a real takeover still shows in the outcome write itself (`Outcome.LOST`).

## [4.0.0] - 2026-11-05

### Changed (breaking)

- Internal classes are no longer public: the whole `service` package (`DefaultAdminOps`, `IdAllocator`, `Names`, `TaskProcessorService` and the rest) is gone from the public API and its classes are package-private in `today.bonfire.oss.bth4j`, as are `CustomThread` and `QueuesHolder`, and the `TaskClient` accessors `store()`, `names()`, `codecs()`, `ids()`, `queues()` and `clock()`. `Codecs` stays public and moves to `today.bonfire.oss.bth4j` (see Added). The loggers of the moved classes keep class-based names, now under `today.bonfire.oss.bth4j` (for example `today.bonfire.oss.bth4j.TaskExecution`, was `today.bonfire.oss.bth4j.service.TaskExecution`); see `Loggers`. The `Misfires` helpers are now `RecurringDefinition.misfireCode`, `misfireMaxFires` and `misfire(String, int)`. `Json` stays public but is documented as internal.
- `EnqueueFailedException.id()` throws `NoSuchElementException` when `ids()` is empty; check `ids()` before reading the first id.
- Redis layout 3. The Redis store needs Redis 7.4 or newer or Valkey 9 or newer, and refuses a namespace written by 3.0 (`init` checks the layout version in `meta`; there is no migration, start with a new namespace). The task hash keeps only short fields so that it stays a listpack: the payload moves to `d:<id>`, the steps to `st:<id>` and the failures to the list `f:<id>` (about half the memory per task with a 300-byte payload). SCHEDULED tasks are in one zset per queue (`sched:<qid>`), the counts are the cardinalities of the state zsets (the `c:<qid>` counters are gone and cannot drift), and the key fields of a finished task expire with the key itself through hash field expiry (the `keys` zset and the RELEASE_KEYS script are gone; `releaseKeys` returns 0 on Redis).
- `ExecutionStore` has a new abstract method `finishCancelledExpired`; custom stores must implement it (see Fixed).
- `InspectionStore` has a new abstract method `idHighWaterMark()`, the first task id not yet allocated; custom stores must implement it (Redis: the id counter plus one, PostgreSQL: the task id sequence, in-memory: the next id).
- `StoreInfo.schemaVersion` is per store and `StoreInfo.SCHEMA_VERSION` is gone: the Redis store reports `RedisTaskStore.LAYOUT_VERSION` (3), the PostgreSQL store `PostgresTaskStore.SCHEMA_VERSION` (2) and the in-memory store 1.
- PostgreSQL schema 2. `init` refuses tables written by 3.0 (schema version 1) before it changes anything; there is no migration, use a new prefix or drop the tables. Schema 2 adds the column `occurrence_id` to `<prefix>_schedule` (see Fixed), and `schemaStatements()` no longer contains an `ALTER TABLE`.
- `TaskEvent.Outcome` has a third value, `UNKNOWN`: a store call that throws (a timeout, a lost reply) is reported as `UNKNOWN` instead of `LOST`, so a committed acknowledgement whose reply was lost no longer looks like a lease loss. `LOST` now means only that the store rejected the transition. The `bth4j.tasks` metric gains the outcome tag value `unknown`. An exhaustive `switch` over `Outcome` must add the case.
- `AdminOps.retry` and `AdminStore.retry` return the new enum `RetryOutcome` (`RETRIED`, `STALE`, `DUPLICATE`) instead of a boolean; callers and custom implementations must adapt (see Fixed).
- The SPI default overloads that only delegated with a null `ScheduleEffect` are removed: `ExecutionStore.ack(id, revision, keep, keepPayload)`, `fail(id, revision, failure, retryAt, keepDead)`, `failExpired(id, revision, failure, retryAt, keepDead)`, `finishCancelled(id, revision, reason, keepPayload)` and `finishCancelledExpired(id, revision, reason, keepPayload)`, `AdminStore.cancel(id, revision, reason)` and `delete(id, revision)`, and `ScheduleStore.putRecurring(definition, nextFire)`. Pass the effect (null for none) to the full forms, and `putRecurring(definition, nextFire, keepUntil)` with `keepUntil = nextFire` for the old meaning. Custom stores and decorators have only the full forms to implement.
- The `afterId` task listing is removed: `TaskClient.tasks(state, queue, afterId, limit)`, `AdminOps.tasks(state, queue, afterId, limit)` and `InspectionStore.tasks(state, queueId, afterId, limit)` are gone, and the cursor form is the only listing (`tasks(state, queue, cursor, limit)` returning a `TaskViewPage`, `TaskPage` on the store; pass a null cursor for the first page). Admin HTTP `GET /api/v1/tasks` always answers `{"items": [...], "next": ...}`: the `after` parameter and the bare JSON array reply are gone, and a missing `cursor` means the first page, like an empty one. Hosts that implement or fake `AdminOps` or `InspectionStore` drop the method.
- `maxRun` is renamed `maxRunTime`, because it is a duration, not a count like `maxAttempts`: `TaskRequest.Builder.maxRunTime(Duration)`, `TaskRequest.maxRunTime()`, `TaskView.maxRunTime()`, `TaskRecord.maxRunTime()` and its builder method, and the admin HTTP task field `maxRunTime`. Storage keeps `max_run_ms` (PostgreSQL) and `mr` (Redis).
- Every attempt now has a maximum run time. A task or schedule without its own `maxRunTime` gets the runner's new `defaultMaxRunTime`, one hour by default (`BackgroundRunner.Builder.defaultMaxRunTime(Duration)`). A task that legitimately runs longer needs its own `maxRunTime` or a larger default. At the limit the attempt gets a cancel request as before. If it is still running one lease-renewal period later, the runner stops renewing its lease (see Added).
- `TaskRequest.Builder.maxRunTime` and `ScheduleDefinition.maxRunTime` accept at most `TaskRequest.MAX_RUN_TIME` (about 24.8 days, `Integer.MAX_VALUE` milliseconds). The PostgreSQL store keeps `maxRunTime` as an int of milliseconds, so a longer value used to fail at enqueue with an `ArithmeticException`; it is now a `TaskValidationException`.
- `ScheduleStore.putRecurring` returns the new enum `PutRecurringOutcome` (`CREATED`, `CHANGED`, `UNCHANGED`) from the same atomic call. A put that would write nothing keeps the revision instead of taking a new one: every field is stored already, the next fire time is kept, and no finished occurrence is recorded as in flight. A runner re-registering its schedules at start therefore no longer makes a concurrent commit of another runner fail its revision check. Custom stores must return the outcome; the paused flag of an existing definition is not compared.
- Records with a new component: `ScheduleDefinition` has `maxRunTime` after `maxAttempts`, `RecurringDefinition` has `maxRunTimeMs` after `maxAttempts`, `ScheduleView` ends with `maxRunTime`, and `RunnerHealth` has `abandonedAttempts` after `runningTasks`. Code that calls the canonical constructors adds the argument.
- `TaskRescheduleException`, `TaskUnrecoverableException`, `TaskLeaseLostException` and `TaskCancelledException` are `final` and extend the new sealed `TaskSignal`, so one `catch (TaskSignal s)` lets the runner's control flow through a processor's own `catch (RuntimeException e)`. Removed as unused: `OperationNotAllowed`, `common.Random`, `common.Errors`, and the byte-array methods of `JsonMapper`, which now has only `fromJson(String, Class)` and `toJson(Object)`.
- API renames for consistent names (storage, Redis keys and PostgreSQL tables and columns are unchanged). "event" meaning the task type becomes "type": `TaskView.type()`, `ScheduleView.type`, `TaskEvent.Deferred.type`, `AdminOps.typeNames()`, `TaskStore.typeId(String)` and `typeNames()`, `typeId` in `TaskRecord` (and its builder), `RecurringDefinition` and `ExpiredLease`, `ClaimRequest.knownTypeIds`; the issue kind `unknown-event` is `unknown-type`; the admin HTTP field `event` is `type`; the Micrometer tag `event` is `type` on `bth4j.tasks`, `bth4j.task.duration` and `bth4j.deferred`; the log MDC key `bth4j.event` is `bth4j.type`. The encoded payload text is `encodedPayload`: `TaskView.encodedPayload()`, the `TaskRecord` component and builder method, and `RecurringDefinition.encodedPayload`. Instants get an `At` suffix: `TaskRecord` and `TaskView` `created` and `stateChanged` are `createdAt` and `stateChangedAt` (components, builder methods, accessors), and the admin HTTP task fields `created` and `stateChanged` are `createdAt` and `stateChangedAt`. `EnqueueFailedException.stored()` is `storedCount()`. `Misfire.CatchUp(int max)` and `Misfire.catchUp(int max)` take `maxFires` (accessor `maxFires()`), and `RecurringDefinition.catchUpMax` is `catchUpMaxFires`. `exceptions/TaskConfigurationError` is `TaskConfigurationException`, and `TaskErrorException` is removed: an unknown queue now throws `TaskValidationException`. `DefaultVtExecutor.getCurrentMaxThreads()` and `getAvailablePermits()` are `currentMaxThreads()` and `availablePermits()`. `ScheduleView` uses the definition's types: `zone` is a `ZoneId` (null when none is stored), `misfire` is a `Misfire`, and `overlapSkip` is `overlap` of type `Overlap`. The admin HTTP schedule fields keep `zone` and `misfire` as text, add `catchUpMaxFires` (only for `CATCH_UP`) and replace `overlapSkip` with `overlap` (`ALLOW` or `SKIP`). `RunnerHealth.running` and `abandoned` are `runningTasks` and `abandonedAttempts`, and so are the admin HTTP health fields; the Micrometer gauge names are unchanged.

### Added

- `BackgroundRunner.builder().failureDetail(FailureDetail.CLASS_NAME_ONLY)` for hosts whose exception messages may carry customer data: the stored failure, the `TaskEvent` error (a `RedactedFailure`), the issues and the runner's log lines then keep the exception class name, the attempt and the time, and no message or stack. `FailureDetail.FULL` is the default and unchanged.

- Cursor listing of tasks: `InspectionStore.tasks(state, queueId, cursor, limit)` returns a `TaskPage(items, next)`, `TaskClient.tasks` and `AdminOps.tasks` have the same form returning a `TaskViewPage`. The cursor is an opaque position in the listing that each store encodes itself (PostgreSQL `<state_changed in epoch microseconds>:<id>`, Redis `<zset score>:<id>`, in-memory `<state_changed in epoch nanoseconds>:<id>`), `next` is null after the last page and a malformed cursor throws `IllegalArgumentException`. Custom `InspectionStore` implementations must add the method. `AdminOps.tasks(state, queue, cursor, limit)` is a new abstract method on a public interface: hosts that implement or fake `AdminOps` must add it.
- Admin HTTP `GET /api/v1/tasks` answers `{"items": [...], "next": ...}` (an empty or missing `cursor` is the first page; see Changed (breaking)). The dashboard's Tasks page pages with `next`.

- Lookup and cancel by unique key. `InspectionStore.taskByKey(key)` returns the task that holds the key now: an open task, or a finished one inside its `keepFor` window; empty when none does (Redis: one GET of `k:<key>` and the task read; PostgreSQL: one lookup through the unique index on `unique_key`, ignoring a key whose `key_until` has passed; in-memory: the same rule). It is a new abstract method: custom stores must implement it. `TaskClient.taskByKey(key)` and `AdminOps.taskByKey(key)` return an `Optional<TaskView>`, and `AdminOps.cancelByKey(key, reason)` cancels the holder with the revision it read and returns the outcome of `cancel`, or the new `CancelOutcome.NOT_FOUND` (no task holds the key) or `CancelOutcome.FINISHED` (the holder already ended and only keeps the key for its window); `STALE` means it changed between the read and the cancel. Hosts that switch exhaustively on `CancelOutcome` must add the two values. Cancelling a waiting fixed-delay occurrence by key pauses its schedule, as cancel by id does. `AdminOps.taskByKey` and `AdminOps.cancelByKey` are new abstract methods: hosts that implement or fake `AdminOps` must add them.
- Admin HTTP `GET /api/v1/tasks/by-key/{key}` (404 when no task holds the key) and `POST /api/v1/tasks/by-key/{key}/cancel` (body `{"reason"}`, no revision; 400 for a blank or over-long key, 404 when no task holds the key, 409 when the holder is already finished or changed meanwhile). The dashboard's Tasks page has a "Find by key" box that opens the holder's task page.

- An attempt that ignores its cancel request is abandoned one lease-renewal period after its maximum run time. Its lease is no longer renewed, so it lapses and maintenance retries or ends the task. Its thread keeps its executor and queue slots until the processor returns. The runner raises the issue `attempt-abandoned` once per attempt; the detail says how many abandoned attempts hold slots. `RunnerHealth.abandonedAttempts`, `BackgroundRunner.abandonedAttempts()`, the gauge `bth4j.runner.abandoned` and the admin health field `abandonedAttempts` count them.
- `ScheduleDefinition.maxRunTime(Duration)` gives each occurrence's attempts a maximum run time. It is stored with the definition (Redis hash field `mr` of `cron:<id>`, PostgreSQL column `max_run_ms` of `<prefix>_schedule`) and shown as `ScheduleView.maxRunTime` and the admin field `maxRunTime`.
- `TaskRequest.MAX_ATTEMPTS` names the largest `maxAttempts` (32767); `TaskRequest.MAX_RUN_TIME` the largest `maxRunTime`.
- `Codecs` (`new Codecs(jsonMapper)`) encodes and decodes payloads and step results exactly as the runner stores them, so a test can pin their stored form without copying the rules.
- `Loggers` names every logger the runner writes to (`RUNNER`, `CLIENT`, `PROCESSOR`, `ATTEMPT`, `MAINTENANCE`, `RECURRING`, `PROMOTION`, `EXECUTOR`, `OBSERVERS`, `TASKS`), and `ROOT` is the prefix all of them except `TASKS` share. The names are class-based and stay fixed when an internal class moves, so log configuration and log capture by name keep working.

### Changed

- `TaskType.interruptOnCancel()` also interrupts a running processor when lease renewal reports a lost lease. Only an attempt actually interrupted for lease loss has its outcome discarded; otherwise completion and failure still go through the store's revision fence and can be applied before takeover. The interrupt is cleared before the thread is reused. Types that did not opt in still learn of lease loss at their next check; unique keys protect task records, so side effects must be fenced or idempotent.
- The Redis scripts collect their zset writes per key and send one variadic command per key at the end of the call, read the task hash with one HMGET and write it with one HSET per task, and compute the revision and the attempt count in Lua: a claim of 32 tasks costs about a third of the commands it did. ENQUEUE receives the queue id, the start-by time and the payload as arguments instead of reading them back, and takes a free unique key with one `SET NX GET`. FAIL appends the new failure in the script instead of reading, extending and rewriting the list from the client. PURGE reads at most max(4 x limit, 1000) entries of tasks whose key window has passed per call, and none whose window is still open.
- Redis: PROMOTE reads each queue's head first (an idle poll costs one command per queue plus two instead of two per queue), CLAIM reads `st:` and `f:` only for tasks that have them, FAIL trims the failure list only when it grew past 20, `renew` sends leases in chunks of 256 in one pipeline, `purgeWorkers` removes at most 500 workers per script call and loops, and a pipelined batch after `SCRIPT FLUSH` loads the script once and resends only the rejected calls.
- `TaskClient.enqueueAll` reserves the ids of a batch with one store call (`IdAllocator.nextIds`); the block end is overflow-checked.
- Redis `heartbeat` no longer mistakes a second heartbeat in the same millisecond for a removed worker; a duplicate unique key reports the holder id as text, so ids above 2^53 are exact.
- `ThroughputContract` (in `bth4j-store-tests`) times confirmed acknowledgements (`Succeeded` with `APPLIED`) instead of processor callbacks, checks every accepted id once in both, and reports batch-enqueue-to-start percentiles; `bth4j.benchmark.tasks`, `.warmups` and `.rounds` set the workload.
- The integration tests run against Redis 8.8 and PostgreSQL 18 (images `redis:8.8-alpine` and `postgres:18-alpine`), and against Valkey 9.1.3 with the Maven profile `valkey`; the images are the properties `bth4j.redis.image` and `bth4j.postgres.image`.
- `TaskClient.putSchedule` logs at INFO only when it created or changed a definition, and at DEBUG when the definition was registered already, so a runner start that re-registers its schedules is quiet.

### Fixed

- Redis enqueue stores a random per-call, per-record write token in task hash field `wt`, in the existing HSET. A transport resend with the same token returns stored before checking the unique key, avoiding a second task or a duplicate-key answer for its own write; another token still returns exists.
- Attempts discarded after a lease-loss interrupt emit `Retrying` with outcome `LOST`, as on a fenced failure, without changing the stored task. Interrupts can close sockets and NIO channels, including pooled database or Redis connections used by a processor on a virtual thread.
- An operator retry inside a unique key's `keepFor` window retains the key without expiry while the task is open, so a same-key enqueue returns `Duplicate` and `taskByKey` still finds it. The keep window starts afresh when the task finishes. If another task holds the retained key, retry returns `DUPLICATE` and changes nothing; the admin HTTP route answers 409 with `code: "KEY_HELD"` next to the error message; the dashboard matches this code. A key already released at completion or after its window is not restored: the retry runs without a key, and an enqueue with that key can start a second task.
- Caller-supplied task ids are checked against the allocation high-water mark and stored content (type, queue, encoded payload when retained, and unique key when the stored task still holds one, including after an operator retry). A mismatch throws `TaskIdReusedException`. `enqueueAll` checks the mark before reserving fresh ids, rejects duplicate caller ids and caller ids inside the fresh range, and compares all caller ids before writing. Requests without caller ids incur no extra reads; caller ids below the end of this client's own allocated block skip the high-water read. Headers, account, attempts, retry policy, start-by, max run time, delay, `at(...)`, `keepFor` duration and payload version are not compared. `prepare()` plus a store's own enqueue skips these caller-id checks. Retries must use the same request, encoded identically; a dropped payload cannot be compared. Redis counter rollback can make an allocated id appear unallocated. PostgreSQL uses `pg_sequence_last_value` (PostgreSQL 10+), requiring only USAGE on the sequence.
- Failed batches expose `EnqueueFailedException.notStored()` with zero-based generated-id positions known not to have been written, including collisions and unattempted chunks. `retryRequests(requests)` preserves ids for uncertain writes and caller-set ids, and leaves known unwritten requests without an id; `TaskRequest.withId(long)` copies a request with an id. Never reuse `ids()` entries at `notStored()` positions, which may belong to other tasks. Generated-id collisions abandon the client's current block and retry from a fresh store block, at most three writes; on exhaustion the colliding positions stay in `notStored()` and no replacement ids are reserved. Batch retries preserve request order and encoded records. Concurrent caller-id reuse after preflight is wrapped in `EnqueueFailedException` and still requires caller correction.
- Id reservation, high-water reads and cold queue/event lookups now throw `EnqueueFailedException` on store failure. Empty `ids()` means nothing was written by this call: resend the same requests unchanged, retaining any caller-set ids. Batch failures before initial reservation completes carry empty ids; later failures carry every request's last assigned id in order, with `notStored()` identifying ids not to reuse. Single `enqueue` retains a caller id even on high-water-read failure, and carries a generated id only once its write was attempted.
- The dashboard ships its Vue runtime (`dashboard/vendor/vue.global.prod.js`, 3.5.13) instead of loading it from a CDN, and the admin HTTP Content-Security-Policy no longer allows `cdn.jsdelivr.net` as a script source, so a compromised CDN cannot run code in an operator's session and the dashboard works without internet access.
- Paging the task listing with `afterId` re-read the cursor task, so a task that left the listed state between pages broke the walk: PostgreSQL ended the listing silently (the task's new `state_changed` is later than every listed row) and Redis restarted from the beginning and repeated tasks. The cursor form (see Added) does not depend on the last task of the previous page and has neither case; a task whose own position moves during the walk can still be seen twice or missed. The `afterId` form is removed (see Changed (breaking)).
- PostgreSQL `allocateIds(1)` took its id with a bare `nextval`, outside the lock that keeps a block allocation contiguous, so it could land inside the range of a concurrent block and two tasks got the same id (the second enqueue reported as accepted and the task was lost). Every count now takes the lock, so single-id allocation is serialised with block allocation and needs the UPDATE privilege on the `meta` table, as block allocation already did.
- Redis `tasks` paging repeated pages without end when a task of an unknown event had been deferred: the cursor was the task's `due` field, but the deferral re-scores it in the queue zset. The cursor is now the score the task has in the zset being paged.
- Redis `purge` could remove nothing for as long as tasks with an open key window sat in front of purgeable ones, because it paged past them on every call. Tasks with a key window are now kept in `hold:<state>:<qid>` (scored by `keyUntil`) instead of `rm:<state>:<qid>`, the zset purge reads, and purge drains `hold` when the window has passed. The layout has these two zsets and the task hash fields `hs` and `fc`, which say whether `st:<id>` and `f:<id>` exist, so that a claim reads those keys only when they do. A namespace written by an earlier 4.0.0 snapshot has layout 2 and is refused by `init`, because it lacks them and a claim would skip its steps and failures.
- `renew` no longer extends a lease that has already expired (Redis and PostgreSQL; the in-memory store follows): the task is reported as not owned and left for the maintenance sweeper. Before, a worker whose renewal came after the expiry but before the sweeper acted kept the lease with an unchanged revision, and the sweeper then ended a cancel-requested task as CANCELLED while the processor was still running, which freed its unique key for a second task.
- The sweeper ends an expired lease of a cancel-requested task with the new `ExecutionStore.finishCancelledExpired`, which does nothing when the lease is no longer expired, like `failExpired`. The worker's own `finishCancelled` is unchanged. Custom `ExecutionStore` implementations must add the method.
- Queue concurrency limits (`QueuePolicy.maxConcurrent`) could lose slots for good: each processor kept its own per-queue counts, so a processor restarted after its thread died counted the inherited tasks but never released them, and a task reclaimed by the same worker while its earlier attempt was still finishing replaced that attempt's entry, so the earlier attempt's slot was never released. The counts now have one owner per runner, shared across processor restarts, and every attempt releases its slot exactly once.
- A lapsed lease can no longer be revived, so `leaseDuration` must sit well above the worst pause of a worker (GC, container freeze, slow store round trip); the minimum of 1 s makes leases of a few seconds fragile.
- An `Error` thrown by a processor is now recorded as a failure and goes through the retry policy, instead of leaving the task leased until its lease expires. `OutOfMemoryError` and other `VirtualMachineError`s (except `StackOverflowError`) are rethrown after being recorded, so the thread's uncaught exception handler still sees them (with their message and stack, which `failureDetail` does not cover). Errors thrown by a retry policy, the store, an observer or the schedule update no longer escape before the task is recorded either. The rethrow of a fatal Error applies to task execution only; in maintenance and the scheduler an Error from an observer or a retry policy is logged and swallowed.
- A fixed-delay schedule could stay parked forever: its next fire time is parked 100 years ahead when the occurrence is created and was set again after the ack in a second call, so a process death or store error between the two left the definition parked, neither paused nor reported. The re-arm after a succeeded occurrence, and the pause after one that ends DEAD, CANCELLED or with an expired lease, now happen in the same atomic step as the transition: `ExecutionStore.ack`, `fail`, `failExpired`, `finishCancelled` and `finishCancelledExpired` take an optional `ScheduleEffect`. The store records the in-flight occurrence of a fixed-delay definition (Redis hash field `occ` in `cron:<id>`, PostgreSQL column `occurrence_id` in `<prefix>_schedule`) and applies the effect only while that id is the finishing task. A re-registration with unchanged timing during the occurrence keeps its re-arm and starts no second occurrence, and neither does a trigger under `Overlap.SKIP` (the commit finds the key held, parks the definition, and the running occurrence re-arms it). Without overlap protection a trigger starts a second occurrence while the first runs; the newer one then owns the re-arm. A stale effect of a replaced or deleted definition does nothing. `AdminStore.cancel` and `delete` take the same optional `ScheduleEffect`, so cancelling or deleting a waiting fixed-delay occurrence pauses its definition atomically (and only when that occurrence is the recorded one). `ScheduleEffect.applied()` reports whether the store changed the definition; the `schedule-paused` issue is raised only then. `AdminOps.pauseSchedule(id, false)` re-arms a fixed-delay definition while it is still paused and resumes it afterwards.
- The runner's misfire advance (`SKIP` and `CATCH_UP`) carries the definition revision and the fire time it read and does nothing when either changed or the definition is paused, so a stale advance can no longer move a freshly registered schedule far into the future or overwrite what another runner wrote. `ScheduleStore.setNextFire(id, revision, expectedFire, next)` is the fenced write; `setNextFire(id, next)` (the operator's trigger and resume) now assigns a new revision.
- `TaskClient.putSchedule` recovers a definition whose stored next fire time was parked or pushed out: the stored time is kept while a fixed-delay occurrence is still running, or while it is not later than the second fire after now (`now + delay` for a fixed delay), otherwise it is recomputed. `ScheduleStore.putRecurring` takes that bound as `keepUntil`.

## [3.0.0] - 2026-10-31

3.0 is a redesign of 2.x: a new public API, a new coordination protocol and a storage interface with Redis,
PostgreSQL and in-memory implementations. 3.0 cannot read 2.x data: drain the 2.x queues before upgrading,
or start 3.0 with a new Redis namespace. Requires Java 21, and Redis 7.0 or newer or PostgreSQL 9.5 or
newer, depending on the store. See `docs/design-3.0.md`.

### Changed (breaking)

- The single `bth4j` artifact is split into `bth4j-core`, `bth4j-redis` and `bth4j-postgres`, with `bth4j-testing` for tests. Applications depend on `bth4j-core` and one store module.
- Task types: `Event` (and the `eventParser` setting) is replaced by `TaskType<T>`, declared once per kind of task with `TaskType.of(name, PayloadClass.class)`, `TaskType.of(name, PayloadCodec)` or `TaskType.of(name)` and `payloadVersion(n)`. The same constant is used to enqueue and to register the processor.
- Producers: `TaskOps` is replaced by `TaskClient`, reached with `BackgroundRunner.client()` or built on its own with `TaskClient.builder()`. `Task` and `Task.Builder` are replaced by the immutable `TaskRequest` (queue, account, `at`, `delay`, `uniqueKey`, `maxAttempts`, headers, `id`, plus `startBy`, `maxRun` and `retryPolicy`). `enqueue` returns `EnqueueResult.Accepted` or `Duplicate` instead of a boolean, and throws `EnqueueFailedException` (carrying the id to retry with) when the store cannot be reached. Recurring definitions are `ScheduleDefinition` with `putSchedule`, `deleteSchedule` and `schedules`.
- Processors: `TaskProcessor<T>` is a functional interface `process(TaskContext, T)`; `dataTypeClass()` is gone. `TaskContext` gives the task, id, attempt, headers, clock, `progress`, `step` and the cancel flag. `TaskCallbacks` and `taskHandlerDecorators` / `recurringTaskHandlerDecorators` are replaced by `TaskObserver` and the sealed `TaskEvent` (`Started`, `Succeeded`, `Retrying`, `Died`, `Rescheduled`, `Cancelled`, `Expired`, `LeaseExpired`, `Deferred`, `ScheduleFired`, `Purged`).
- Task ids are 64-bit numbers allocated by the client in blocks (`TaskClient.nextId()`, `idBlockSize`); the text ids with the `|` separator and the pipe-separated task string are gone. Queue names and task type names are stored as numeric ids from registries in the store, and there are no foreign keys.
- The coordination protocol is lease and revision based. Every state change is one atomic store call that checks the task's `revision` (the fence); a worker that lost its lease cannot complete, fail, reschedule or checkpoint the task. The stale-task timeout, the lock-based maintenance and the lease token are gone: `leaseDuration` replaces `staleTaskTimeout`, and an expired lease is retried by `failExpired`, which also leaves a lease alone that was renewed after the expiry scan.
- Task states are QUEUED, SCHEDULED, LEASED, SUCCEEDED, DEAD, CANCELLED and EXPIRED. Succeeded tasks are kept (10 minutes by default) instead of removed, dead tasks are kept 90 days by default, and a retention of zero removes the record at the transition. A task ends CANCELLED when an operator cancels it, when its processor throws `TaskCancelledException` or when it runs past `maxRun`, and EXPIRED when its `startBy` passes before it started; both are kept for `cancelledRetention` (48 hours by default).
- Failures are recorded on the task (the last 20, with type, message and stack). Retries follow a `RetryPolicy` (exponential backoff with jitter by default) instead of `taskRetryDelay` and `Event.retryCount()`; the attempts are `maxAttempts` per request, `defaultMaxAttempts` (10) otherwise.
- `BackgroundRunner`: `BackgroundRunner.builder()` replaces `new BackgroundRunner.Builder()`, `start()` replaces `run()` and `stop()` replaces `stopRunner()`; new `quiet()`, `resume()`, `registry()`, `client()` and `workerId()`. The builder takes `store(FullStore)` instead of `jedisClient` and `namespacePrefix`, `concurrency(Concurrency)` instead of choosing an executor, and its settings were renamed or added: `idlePollInterval` replaces `taskProcessorQueueCheckInterval`, `scheduledTasksCheckInterval` replaces `delayedTasksQueueCheckInterval`, `serviceCheckInterval` replaces `BGThreadCheckInterval`, `succeededRetention`, `deadRetention`, `cancelledRetention`, `keepSucceededPayload`, `purgeInterval`, `purgeBatchSize`, `claimBatchSize`, `idBlockSize`, `defaultMaxAttempts`, `workerLabel`, `observer`, `retryPolicy`, `clock`, plus `retryPolicy(name, policy)`, `queue(name, QueuePolicy)` and `workerStaleAfter`. `cronLockDuration` and `recurringTasksQueueAheadDuration` are gone; occurrences are created when they come due.
- Concurrency: the default is a fixed limit of twice the number of processors on virtual threads; `Concurrency.adaptive(min, max)` keeps the adaptive limit. `DefaultPtExecutor` is removed. `BackgroundExecutor` has the contract `reserve(max, wait)`, `release(n)`, `execute`, `activeCount`, `shutdown`, `awaitTermination`; `isPoolFull` and `getExecutor` are gone.
- Unknown task types: a runner claims only the types it has processors for (PostgreSQL filters in the claim query, Redis defers them 5 seconds without an attempt, the in-memory store skips them).
- Recurring definitions: each fire time creates one task exactly once across instances (the commit compares the definition revision and the fire time); missed fire times are skipped; re-registering with the same expression keeps the next fire time; definition revisions come from a counter that never resets.
- `stop()` waits for services and running tasks up to `shutdownTimeout` (default 30 seconds), keeps renewing the leases of running tasks meanwhile, and shuts down the task executor.
- The Redis key layout lives in `bth4j-redis` (`THC` is gone). All keys carry the namespace as a hash tag, so the store works on Redis Cluster, and every transition is one Lua script that reads Redis time.
- `QueuesHolder` holds logical queue names; the default queues are `Q:DEF`, `Q:LOW`, `Q:MED` and `Q:HIGH` with `Q:DEF` as default.

### Added

- `bth4j-core`: `TaskType`, `PayloadCodec`, `TaskRequest`, `Uniqueness`, `EnqueueResult`, `TaskClient`, `TaskProcessor`, `TaskContext`, `TaskView`, `TaskProcessorRegistry`, `RetryPolicy`, `TaskObserver`, `TaskEvent`, `Concurrency`, `ScheduleDefinition`, and the store SPI in `today.bonfire.oss.bth4j.spi` (`TaskStore`, `ExecutionStore`, `MaintenanceStore`, `ScheduleStore`, `InspectionStore`, `FullStore`, `TaskRecord`, `TaskState`).
- `bth4j-redis`: `RedisTaskStore(UnifiedJedis, namespace)`: one hash per task with only the fields that are set, sorted sets for queues and state indexes, one Lua script per transition. Requires Redis 7.0 or newer because the scripts read the clock before writing (effect replication).
- `bth4j-postgres`: `PostgresTaskStore(DataSource, prefix)`: tables `<prefix>_task`, `_queue`, `_event`, `_worker`, `_schedule` and `_meta`, partial indexes per state, claims with one bounded index scan per queue under `FOR UPDATE SKIP LOCKED`, revision-checked `UPDATE` statements. `init()` creates the schema under an advisory lock and `schemaStatements()` provides the DDL for migration tools. Uses only `java.sql`. The SQL uses `FOR UPDATE SKIP LOCKED` and `ON CONFLICT`, so PostgreSQL 9.5 or newer is required; it is tested on 17.
- `bth4j-testing`: `InMemoryStore` and `MutableClock` for tests of applications.
- `bth4j-store-tests`: `StoreContract`, the tests every store must pass; all three stores run it. Not published.
- Steps: `TaskContext.step(name, ...)` stores the result of each step durably, so a retry resumes after the last completed step. At least once per step; side effects belong inside steps.
- Unique keys with a keep window (`Uniqueness.keepFor(duration)`), enforced by a partial unique index in PostgreSQL and a key string in Redis.
- Client-allocated ids and safe enqueue retries after a lost reply (`TaskClient.nextId()`, `TaskRequest.Builder.id`).
- Progress text for operators (`TaskContext.progress`), account labels and headers on tasks, a worker registry with a label per runner.
- Retention and purge per terminal state, with unique-key release; `quiet()` and `resume()` on the runner.
- Inspection on the client: `task(id)`, `counts()` and `tasks(state, queue, afterId, limit)`.
- Builder settings are validated, and `build()` fails early on a missing store or an invalid queue configuration.
- GitHub Actions workflows for pull request builds, CLA checks and releases, using the shared BonfireTrunk workflows.
- `CHANGELOG.md` and a Contributing section in the README.
- Cancel: `AdminOps.cancel(id, revision, reason)` cancels a QUEUED or SCHEDULED task at once and asks a LEASED task to stop; the runner learns of it when it renews the lease, `TaskContext.cancelRequested()` and `checkCancelled()` show it to the processor, and the task ends CANCELLED with the reason kept on the record. `TaskType.interruptOnCancel()` also interrupts the processor's thread.
- `startBy` is enforced: a QUEUED or SCHEDULED task whose `startBy` passed is never claimed, maintenance moves it to EXPIRED and the runner emits `TaskEvent.Expired`.
- `maxRun` is enforced: a task running longer than `maxRun` gets a cancel request ("max run time ... exceeded") from the lease renewal and ends CANCELLED.
- Named retry policies: `BackgroundRunner.builder().retryPolicy(name, policy)` registers one and `TaskRequest.retryPolicy(name)` picks it; an unknown name uses the default policy and records an issue.
- Queue policies: `BackgroundRunner.builder().queue(name, QueuePolicy)` gives a queue a `weight` for its share of the free slots and a `maxConcurrent` limit on this runner.
- Queue pause and resume: `AdminOps.pauseQueue(queue, paused)` stops every runner from claiming from the queue; tasks can still be enqueued to it.
- Health: `BackgroundRunner.health()` returns a `RunnerHealth`, `issues()` returns the last 100 `Issue`s the runner recorded, and `drain(Duration)` goes quiet and waits for the running tasks.
- Worker registry: runners write a heartbeat (`lastSeen`, `running`) every `maintenanceCheckInterval`, and maintenance deletes workers silent for `workerStaleAfter` (10 minutes by default).
- `AdminOps`, the operator view and operations over one store (counts, queues, tasks, retry, cancel, delete, workers, schedules, health, issues), reached with `BackgroundRunner.admin()` or `TaskClient.admin()`; the SPI has the new `AdminStore` in `FullStore`.
- `TaskClient.prepare(TaskRequest)` returns the validated `TaskRecord`, and `PostgresTaskStore.enqueue(Connection, TaskRecord)` stores it inside the caller's transaction.
- Schedules: fixed-delay definitions (`ScheduleDefinition.every(id, type, payload, delay)`, re-armed when an occurrence succeeds and paused when an occurrence ends dead or cancelled), `zone(ZoneId)` for cron, `misfire(Misfire.SKIP | FIRE_ONCE_NOW | catchUp(max))`, `overlap(Overlap.SKIP)`, and pause, resume and trigger through `AdminOps`.
- `LoggingTaskObserver`: one SLF4J line per `TaskEvent` with `bth4j.task`, `bth4j.event` and `bth4j.queue` in the MDC.
- `bth4j-micrometer`: `MicrometerTaskObserver` (counters `bth4j.tasks`, `bth4j.deferred`, `bth4j.schedule.fired`, `bth4j.purged` and timer `bth4j.task.duration`) and `MicrometerRunnerMetrics.bind` (gauges `bth4j.runner.running`, `bth4j.runner.up` and `bth4j.tasks.state`); `micrometer-core` is a provided dependency.
- `bth4j-admin-http`: `AdminHttpServer`, a JSON admin API over `AdminOps` on the JDK HTTP server with users, roles (`ADMIN`, `VIEWER`), cookie sessions, CSRF tokens, optional CORS and HTTPS, and static file serving.
- `dashboard/`: a Vue 3 operator dashboard without a build step (overview, queues, tasks, dead tasks, schedules, workers, issues), served by `AdminHttpServer.staticDir` or any static host.
- Redis: the keys `paused`, `startby`, `workers` and `crondefs`, the fields `seen` and `running` on `w:<id>`, the fields `zone`, `mf`, `cum`, `fd`, `os` and `paused` on `cron:<id>`, and the scripts CANCEL, FINISH_CANCELLED, RETRY, DELETE, EXPIRE, PURGE_WORKERS, CRON_PAUSE and CRON_SET_NEXT. `reclaim`, `dueRecurring` and `heartbeat` are plain commands (24 scripts in all), and the reverse registry hashes `reg:*:names` and the `queues` set are gone: listings invert `reg:queue` and `reg:event`, purge walks the values of `reg:queue`.
- PostgreSQL: `<prefix>_worker.running`, and `<prefix>_schedule` columns `zone`, `misfire`, `catch_up_max`, `fixed_delay_ms`, `overlap_skip` and `paused` with the partial index `_due (next_fire) WHERE NOT paused`; the schema version stays 1.

### Removed

- `DefaultPtExecutor`, `THC`, and the single `bth4j` artifact.
- Text task ids, the pipe-separated task string and the locks of the stale/lock based protocol.
